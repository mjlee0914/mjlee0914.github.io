## 1. 왜 RAG로 분리배출을 안내했을까?

분리배출 규정은 단순한 상식 문제가 아니다. 자치구마다 규정이 다르고, 답은 조례 본문뿐 아니라 시행규칙의 별표, 병합된 표 셀, 비고와 예외 조건에도 흩어져 있다. 언어 모델이 학습한 일반 지식만으로 답하면 다른 지역의 규정을 섞거나 존재하지 않는 내용을 자신 있게 말할 수 있다.

분리당은 이 문제를 다음 원칙으로 풀었다.

1. 서대문구와 송파구의 **공식 문서에서만** 근거를 찾는다.
2. 질문의 동·구를 해석해 **해당 지역의 문서만** 검색한다.
3. 찾은 근거 안에서만 답하고 **출처를 함께 제시**한다.
4. 지역이 모호하거나 조건이 부족하면 되묻는다.
5. 근거가 없으면 추측하지 않고 **정보 부족**이라고 답한다.

즉, 목표는 “무엇이든 대답하는 챗봇”이 아니라 **근거가 있을 때만 답하는 검색 시스템**이었다.

---

## 2. RAG란 무엇인가?

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 언어 모델이 바로 답을 만들게 하지 않고, 먼저 외부 지식에서 관련 근거를 검색한 뒤 그 근거를 모델 입력에 넣어 답을 생성하는 방식이다.

```text
사용자 질문
   ↓
질문 해석·검색어 보정
   ↓
문서 검색(Retrieval)
   ↓
관련 근거 선택
   ↓
질문 + 근거를 LLM에 전달
   ↓
근거 기반 답변 생성(Generation)
   ↓
인용 검증·평가·실행 기록
```

일반적인 LLM 답변과 비교하면 차이는 다음과 같다.

| 구분 | 일반 LLM | RAG |
| --- | --- | --- |
| 지식 | 모델 학습 데이터에 의존 | 외부 문서를 실행 시점에 검색 |
| 최신·지역 정보 | 틀리거나 섞일 수 있음 | 검색 자료를 교체해 반영 가능 |
| 근거 확인 | 어려움 | 검색한 문서와 위치를 제시 가능 |
| 실패 처리 | 그럴듯하게 추측할 위험 | 검색 실패를 감지해 답변 보류 가능 |
| 추가 비용 | 주로 생성 호출 | 임베딩·검색·재정렬·생성 비용 발생 |

RAG라고 해서 자동으로 정확해지는 것은 아니다. 잘못 쪼갠 문서는 검색되지 않고, 올바른 문서가 검색되어도 순위가 낮으면 모델에게 전달되지 않는다. 또한 모델이 근거를 잘못 해석할 수도 있다. 그래서 **데이터 품질, 검색 품질, 생성 품질을 분리해 평가하는 것**이 중요하다.

## 3. 분리당의 전체 파이프라인

분리당의 Streamlit 화면과 평가 실행기는 같은 공통 `RAGPipeline.run()`을 호출한다. 시연 화면만 잘 작동하고 평가 코드는 다른 경로를 쓰는 상황을 피하기 위한 선택이다.

```text
공식 조례·시행규칙·HWP 별표 수집
   ↓
원문 검수·표 구조 복원
   ↓
조문·표 행 단위 청킹 + 출처 메타데이터 보존
   ↓
OpenAI 임베딩 → 로컬 JSON 벡터 색인
   ↓
동 → 구 지역 해석 / 질문 다듬기
   ↓
A 벡터 검색
B BM25 + 벡터 검색(RRF)
C B 후보 + LLM 재정렬
   ↓
선택된 근거로 답변 생성
   ↓
인용 검증·응답 상태 결정
   ↓
Langfuse 실행 추적 + Ragas/Hit@k 평가
```

### 3-1. 수집과 전처리

프로젝트는 서대문구·송파구의 조례와 시행규칙 XML 4건, HWP 첨부 19건을 다뤘다. 특히 HWP 별표의 병합 셀과 줄바꿈은 그대로 추출하면 한 문장이 여러 행으로 갈라지거나 머리글·비고·예외가 본문과 분리됐다.

따라서 표의 머리글과 병합 셀 정보를 각 행에 붙이고, 원래 행·셀 ID와 원문 위치는 유지했다. 검색을 위해 글자를 보정하더라도 원문 `text` 자체는 바꾸지 않는 원칙을 세웠다. RAG에서 전처리는 단순한 청소가 아니라 **검색 가능한 지식으로 만드는 모델링 과정**이라는 점을 배웠다.

### 3-2. 청킹과 임베딩

청킹(chunking)은 긴 문서를 검색 가능한 작은 단위로 나누는 작업이다. 너무 크게 나누면 관련 없는 내용이 섞이고, 너무 작게 나누면 조건과 예외가 떨어져 나간다. 분리당은 조문과 표 행을 중심으로 543개 청크를 만들었고, 그중 표 행이 432개였다.

각 청크는 OpenAI의 `text-embedding-3-small`로 벡터화했다. 임베딩은 문장을 의미를 나타내는 숫자 배열로 바꾸는 과정이며, 질문 벡터와 문서 벡터의 코사인 유사도로 의미상 가까운 근거를 찾는다.

### 3-3. 지역 해석과 질문 다듬기

“연희동에서 종이팩은 어떻게 버려요?”처럼 동 이름이 들어오면 서울 행정동·법정동 매핑표로 자치구를 판별한다. 지역이 충돌하거나 지원 범위 밖이면 무리하게 검색하지 않고 재질문한다.

또한 “우유팩”, “두유팩”, “소주팩”을 공식 품목명 “종이팩”으로 보완하는 품목 사전을 사용했다. 다만 질문 다듬기가 실패하면 원질문으로 검색하도록 해, 보정 기능 하나가 전체 검색을 막지 않게 했다.

### 3-4. A/B/C 검색

세 가지 검색 방식을 같은 평가셋으로 비교했다.

| 방식 | 구성 | 장점 | 한계 |
| --- | --- | --- | --- |
| A | 벡터 검색 | 표현이 달라도 의미가 비슷한 문서를 찾기 좋음 | “대형폐기물” 같은 정확한 단어와 숫자·표 행에 약할 수 있음 |
| B | 벡터 + BM25를 RRF로 결합 | 의미 검색과 키워드 검색의 장점을 함께 사용 | 결합 후보 안에서 정답이 2~5위에 머물 수 있음 |
| C | B의 후보를 LLM으로 재정렬 | 질문과 근거의 관련성을 다시 판단해 정답을 위로 올림 | 모델 호출이 추가돼 느리고 비용이 증가 |

BM25는 단어의 등장 빈도와 문서 내 희소성을 이용하는 전통적인 키워드 검색이다. 벡터 검색이 의미 유사성에 강하다면 BM25는 정확한 용어에 강하다. 두 결과는 RRF(Reciprocal Rank Fusion)로 결합했다. RRF는 서로 다른 점수 체계를 직접 비교하지 않고 각 결과의 **순위**를 이용해 합치는 방법이다.

C 방식은 결합 후보 20개를 LLM이 다시 읽고 관련도 순으로 재정렬했다. 최종 서비스 화면에서는 평가상 가장 높은 Hit@5를 기록한 C를 사용했다.

### 3-5. 답변 생성과 인용 검증

검색 결과를 그대로 보여 주는 데서 끝나지 않고, 선택된 근거만 답변 모델에 전달했다. 응답은 `answered`, `needs_clarification`, `insufficient_evidence`, `error`처럼 상태를 구분했다.

모델이 답변에 붙인 인용이 실제 입력 근거 안에 존재하는지도 코드로 다시 확인했다. 이 단계가 없으면 답은 그럴듯해도 출처가 엉뚱한 “인용 환각”이 생길 수 있다.

### 3-6. 관찰과 평가

검색은 Hit@1·Hit@5로, 답변은 정답 충족·근거 적합·근거 없음 대응으로 평가했다. Ragas는 Faithfulness와 Answer Relevancy 등을 계산하고, Langfuse는 질문·후보·답변·인용·점수를 하나의 실행 ID에 묶어 추적했다.

이렇게 하면 실패가 생겼을 때 “검색이 못 찾았는가”, “찾았지만 순위가 낮았는가”, “근거는 맞지만 생성이 틀렸는가”를 나누어 볼 수 있다.

## 4. 팀원별 역할과 연결 구조

다섯 명이 기능을 나눴지만 각자의 결과가 다음 사람의 입력이 되도록 공통 계약과 인계 기준을 맞췄다.

| 팀원 | 담당 | 주요 산출물 |
| --- | --- | --- |
| 양석호 | 공통 기반·통합 | 요청/응답 계약, 로더·청킹·색인, `RAGPipeline`, 실행 기록, 평가 실행기, `POST /chat` 기반 |
| 강성수 | 답변·평가·품질 추적 | 근거 기반 답변, 재질문·정보 부족·오류 구분, 인용 검증, Ragas, Langfuse, CI·보안 검사 |
| 이정은 | 자료·정제·질문 다듬기 | 공식 자료 수집, HWP 별표 전처리, 원문 검수, 품목 별칭 사전, 질문 다듬기 |
| **이명지** | **검색·지역·장소** | **동→구 해석, A/B/C 검색, 색인, Hit@5, getSpot 장소 조회 구조** |
| 이승주 | 청킹·화면·검증 | 표 청킹 개선, 최종 평가셋, Streamlit 챗봇, 검색 후보·인용 검증 패널 |

협업에서 중요한 점은 “파일을 나눠 가졌다”가 아니라 **입출력을 연결했다**는 것이다. 예를 들어 청킹이 바뀌면 이명지는 새 청크를 재색인하고, 강성수는 새 `chunk_id`로 답변과 인용을 확인해야 했다. 질문 다듬기가 바뀌면 원질문·변환 질의·보존할 조건을 검색 담당에게 전달했다.

## 5. 내가 맡은 검색·지역·장소 조회

### 지역을 먼저 정한 이유

같은 품목도 자치구별 규정이 다르므로, 검색 후에 지역을 고르는 것보다 **검색 전에 지역 필터를 적용**하는 편이 안전하다. `src/retrieval/regions.py`에서 동·구 입력을 해석하고, 애매하거나 충돌하면 검색하지 않고 되묻도록 했다.

### 벡터 검색만으로 부족했던 장면

초기 A 검색에서는 “송파구 대형폐기물”처럼 정확한 단어가 중요한 질문의 정답 근거가 3위로 밀렸다. 의미상 비슷한 조문이 먼저 나온 것이다. BM25를 합친 B에서는 2위, LLM 재정렬을 적용한 C에서는 1위로 올라갔다.

이 경험으로 “임베딩이면 의미를 이해하니 충분하다”는 생각이 틀렸다는 것을 배웠다. 법규·표·가격·품목처럼 정확한 단어가 중요한 데이터는 키워드 검색과 결합해야 했다.

### Hit@k를 사용한 이유

생성 답변만 보면 검색과 생성의 실패가 섞인다. 그래서 허용된 정답 청크 ID가 상위 `k`개 후보 안에 있는지를 보는 Hit@k를 구현했다. Hit@5가 낮으면 답변 모델을 바꾸기 전에 검색·청킹·색인을 먼저 개선해야 한다.

### 장소 조회는 왜 별도 경로인가?

분리배출 규정은 공식 문서 RAG로 답하지만, 수거함 위치 같은 정보는 실시간 장소 API가 더 적합하다. `getSpot` 응답을 `PlaceLookupResult`로 정리해 파이프라인에 연결할 수 있는 구조를 만들었다. 다만 최종 발표 시점에는 실제 장소 API와 지도 표시까지 완성하지 못해 도전 과제로 남았다.

## 6. 사용한 도구와 선택 이유

| 도구 | 사용 목적 | 선택 이유·차별점 |
| --- | --- | --- |
| Python 3.13 + uv | 실행 환경·의존성 고정 | `pip`만 사용할 때보다 잠금 파일 기반 재현이 쉽고 설치가 빠름 |
| LangChain | 임베딩·모델 어댑터와 실행 구성 | 모델 제공자를 교체 가능한 형태로 연결하기 쉬움. 단, 핵심 파이프라인 계약은 프로젝트 코드로 명시 |
| OpenAI `text-embedding-3-small` | 문서·질문 임베딩 | 관리형 API라 빠르게 실험 가능. 로컬 임베딩보다 운영은 간단하지만 비용·외부 전송 고려 필요 |
| BM25 (`rank-bm25`) | 키워드 검색 | 임베딩이 놓치는 정확한 품목명·숫자·법규 용어를 보완 |
| RRF | 벡터·BM25 결과 융합 | 서로 단위가 다른 점수를 정규화하지 않고 순위만으로 안정적으로 결합 |
| LLM reranker | 후보 재정렬 | 별도 cross-encoder 없이 질문과 후보의 관련도를 유연하게 판단. 대신 호출 시간과 비용이 큼 |
| 로컬 JSON 색인 | 프로젝트용 벡터 저장 | 작은 데이터에서 구조를 이해하고 재현하기 쉬움. 대규모 동시 검색·필터링에는 한계 |
| Streamlit | 챗봇·검증 화면 | Python만으로 빠르게 시연하고 내부 검색 후보까지 함께 표현 가능. 정교한 프론트엔드에는 제약 |
| Langfuse | 실행 추적·점수 연결 | 질문부터 후보·답변·평가까지 한 실행 ID로 관찰 가능 |
| Ragas | RAG 답변 평가 | 단순 정답 일치 외에 근거 충실도·관련성을 볼 수 있음. 모델 판정 편차 때문에 사람 검토와 병행 필요 |
| pytest·Ruff·mypy | 테스트·정적 검사 | 동작 회귀, 문법·스타일, 타입 오류를 서로 다른 층에서 확인 |
| Gitleaks·Dependabot·Codecov | 보안·의존성·커버리지 | API 키 유출과 취약 의존성을 점검하고 테스트 범위를 확인 |

### 왜 OpenSearch를 바로 쓰지 않았을까?

OpenSearch는 BM25, 벡터 검색, 필터링과 대용량 운영 기능을 한 시스템에서 제공한다. 반면 이번 프로젝트는 543개 청크로 RAG의 기본 흐름과 검색 방식 차이를 학습하는 것이 우선이었다. 로컬 JSON 색인은 내부 동작을 확인하고 A/B/C를 빠르게 비교하기에 단순했다.

따라서 **OpenSearch는 구현 완료 도구가 아니라 검색 시스템 v2의 개선 목표**다. 데이터 규모, 동시 요청, 색인 갱신이 커질 때 도입하고 같은 평가셋의 Hit@5·응답 시간·비용으로 기존 방식과 비교해야 한다.

---

## 7. 최종 실험 결과

최종 평가는 답변 가능 17문항과 근거 없음 3문항, 총 20문항을 사용했다. A/B/C를 각각 20건, C+질문 다듬기를 20건 실행해 총 80건을 비교했다.

| 구성 | Hit@1(/17) | Hit@5(/17) | 정답 충족(/17) | 근거 없음 대응(/3) | 평균 응답 시간 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A 벡터 | 4 | 5 | 3 | 3 | 1.59초 |
| B 벡터+BM25 | 3 | 8 | 6 | 3 | 1.66초 |
| C LLM 재정렬 | 12 | 12 | 10 | 3 | 5.19초 |
| C+질문 다듬기 | 12 | 12 | 9 | 3 | 4.98초 |

해석할 때 주의할 점이 있다.

- C가 가장 높은 Hit@5를 기록했지만 A·B보다 약 3배 느렸다.
- C는 상위 5개 안에 들어온 정답을 모두 1위로 올렸다.
- 근거 없음 3문항은 네 구성 모두 추측하지 않고 정보 부족으로 답했다.
- 질문 다듬기는 이 20문항에서 분명한 이득을 보이지 않았다.
- 표본이 작고 구성별 실행이 1회라 비율을 일반화할 수 없다.
- 정답 충족과 근거 적합은 모델 판정이어서 흔들릴 수 있으므로 검색 비교에서는 Hit@k를 더 신뢰했다.

이 결과는 “가장 정확한 도구 하나”를 고르는 문제가 아니라 **품질·응답 시간·호출 비용 사이의 선택**임을 보여 준다.

## 8. 프로젝트의 의의와 배운 점

### 1) RAG의 성능은 데이터에서 시작한다

좋은 모델을 붙여도 표의 머리글과 예외가 청크에서 사라지면 정답을 찾을 수 없다. 데이터 수집, 원문 검수, 청킹, 메타데이터가 생성 모델만큼 중요했다.

### 2) 검색과 생성을 분리해서 봐야 한다

검색하지 못한 답은 모델이 만들 수 없다. 반대로 정답 청크가 1위여도 생성이 필수 사실을 빠뜨릴 수 있다. Hit@k, 답변 품질, 인용 검증을 나눠 본 이유다.

### 3) 의미 검색과 키워드 검색은 경쟁 관계가 아니다

벡터 검색은 표현 차이에 강하고, BM25는 정확한 단어에 강했다. 하이브리드 검색과 재정렬은 각 방법의 약점을 보완했다.

### 4) “모른다”는 것도 중요한 품질이다

분리배출처럼 지역에 따라 답이 달라지는 영역에서는 그럴듯한 오답보다 정보 부족 안내가 낫다. 근거 없음 3문항을 모두 거절한 결과는 정확한 답변 수만큼 중요했다.

### 5) 평가 데이터도 오류가 있을 수 있다

실행 후 질문이 실제 근거와 어긋난 문항을 발견했다. 공식 결과는 그대로 보존하고 정정판을 별도로 두었다. 평가셋을 정답으로 맹신하지 않고 원문으로 다시 확인해야 했다.

### 6) 협업은 역할보다 인계가 중요하다

청킹 변경은 색인과 정답 청크 ID를 바꾸고, 검색 변경은 답변·인용·평가에 영향을 준다. 각자 코드를 작성하는 것보다 변경 사항을 다음 담당자에게 어떤 형식으로 전달할지가 중요했다.

## 9. 한계와 보완 방향

### 데이터·검색

- **송파구 시행규칙 표 행 검색 실패:** C가 놓친 도달 가능한 4문항이 모두 이 유형이었다. 표 제목·상위 항목·단위·조건을 청크 검색문에 더 명시하고 전후 Hit@5를 비교해야 한다.
- **작은 평가셋:** 답변 가능 문항이 17개뿐이고 표 행 비중이 높다. 실제 사용자 질문을 수집해 지역·품목·표현 유형별로 확장해야 한다.
- **로컬 색인의 운영 한계:** OpenSearch를 도입해 BM25·벡터·메타데이터 필터를 통합하고, 기존 방식과 동일한 기준으로 비교할 필요가 있다.

### 생성·평가

- **판정 모델의 흔들림:** 같은 답변의 Faithfulness가 0과 1로 달라진 사례가 있었다. 규칙 기반 검사, 다회 판정, 사람 검토 표본을 함께 사용해야 한다.
- **재정렬 비용과 지연:** 후보 수를 조절하거나 cross-encoder 같은 전용 reranker를 비교해 품질을 유지하면서 호출 비용을 줄여야 한다.
- **후보 기록 범위:** 최종 5개뿐 아니라 재정렬 전 20개 후보 전체의 순위와 점수를 저장하면 실패 원인을 더 정확히 분석할 수 있다.

### 서비스

- **지원 지역 제한:** 현재는 서대문구·송파구만 지원한다. 다른 구를 추가할 때는 문서 수집·검수·평가셋 제작 절차도 함께 자동화해야 한다.
- **장소 조회 미완성:** 실제 장소 API, 지도 표시, 운영 오류 처리와 캐시 정책을 연결해야 한다.
- **실사용 검증 부족:** 공개 배포 환경의 동시 요청, 비용, 응답 시간 목표와 사용자 피드백은 아직 측정하지 않았다.
- **규정 최신성:** 조례 개정 시 수집 날짜와 문서 버전을 확인하고 재색인·회귀 평가하는 주기적 파이프라인이 필요하다.

---

## 10. 마무리

이 프로젝트를 통해 RAG가 단순히 “문서를 벡터 DB에 넣고 LLM에 연결하는 기술”이 아니라는 것을 알게 됐다. 실제로는 원문을 보존하는 전처리, 검색 가능한 청킹, 지역 필터, 하이브리드 검색, 재정렬, 인용 검증, 평가셋과 관찰 도구가 함께 움직여야 했다.

특히 내가 맡은 검색 영역에서는 벡터 검색의 의미 유사성만 믿지 않고 BM25와 재정렬을 비교하면서, **좋은 답변의 출발점은 좋은 근거를 올바른 순위로 찾는 것**임을 배웠다. 아직 OpenSearch와 실제 장소 연동, 더 큰 평가셋이 남아 있지만, 모르는 것을 지어내지 않고 실패 이유를 추적할 수 있는 RAG의 기본 구조를 끝까지 연결해 본 것이 이번 프로젝트의 가장 큰 의미였다.
