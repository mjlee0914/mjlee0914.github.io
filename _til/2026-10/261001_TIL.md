## 1. Synchronous and Asynchronous Work

Synchronous statements run in order. Each statement finishes before JavaScript moves to the next one. A long synchronous task keeps the main thread busy, so the browser cannot respond to input or update the page until that task finishes.

Asynchronous APIs let JavaScript start work and continue running other code while it waits. When the timer, user event, or network request is ready, its callback is queued. The event loop can run that callback after the current JavaScript task finishes.

A timer delay is a minimum wait, not a promise that the callback runs at that exact time. Promise handlers are queued as microtasks; timer callbacks are tasks. After the current task, the browser drains the microtask queue before it moves on to another task.

## 2. HTML Parsing and DOM-Ready JavaScript

The HTML parser reads the document from top to bottom. A classic script without <code>async</code>, <code>defer</code>, or <code>type="module"</code> runs as soon as the parser reaches it and pauses parsing while the script runs. If that script is in the <code>&lt;head&gt;</code>, later elements such as a button may not exist yet.

There are three common ways to wait until the elements are available:

1. Put the script just before <code>&lt;/body&gt;</code>.
2. For an external script, use <code>defer</code>. It downloads during parsing and runs after parsing finishes, before <code>DOMContentLoaded</code>.
3. Register a <code>DOMContentLoaded</code> listener. It runs after the HTML has been parsed and deferred scripts have run.

<code>async</code> is different: an external async script runs as soon as it finishes downloading. Its order is not guaranteed, and it may run before the DOM is complete. <code>DOMContentLoaded</code> does not wait for async scripts.

~~~html
<script>
  document.addEventListener("DOMContentLoaded", function () {
    const button = document.querySelector("#save");
    button.textContent = "Ready";
  });
</script>
<button id="save">Waiting for the DOM</button>
~~~

## 3. <code>this</code>, <code>parent</code>, and <code>top</code>

These names do not always point to the same object.

- In a classic browser script at the top level, <code>this</code> is the page's global object, <code>window</code>. Top-level <code>this</code> in a JavaScript module is <code>undefined</code>.
- Inside an iframe, that frame's <code>window</code> is its own global object. <code>window.parent</code> points to its immediate containing window; <code>window.top</code> points to the outermost window.
- In a top-level page that is not inside an iframe, <code>window</code>, <code>window.parent</code>, and <code>window.top</code> refer to the same window.
- In a normal function used as an event listener, <code>this</code> is the element the listener is attached to, matching <code>event.currentTarget</code>. An arrow function keeps <code>this</code> from its surrounding scope.

The demo is itself shown in an iframe, so it displays how these relationships differ from a top-level page.

## 4. <code>innerHTML</code>, <code>innerText</code>, and <code>textContent</code>

These properties expose different views of an element's contents.

- <code>innerHTML</code> reads or replaces the child markup as an HTML string. Assigning markup parses it into elements. Do not put untrusted strings into <code>innerHTML</code>; use <code>textContent</code> for plain text.
- <code>textContent</code> reads or replaces the text in all descendant nodes, including text that is hidden by CSS.
- <code>innerText</code> reflects rendered, visible text and is affected by styling and layout.

Use the demo buttons to compare the values. Its markup example is fixed and trusted.

## 5. Browser Events and Event Propagation

<code>addEventListener()</code> lets several independent listeners respond to the same event. Assigning a function to <code>element.onclick</code> uses one handler slot, so a later assignment replaces the earlier <code>onclick</code> function.

A bubbling event moves through three phases:

1. **Capturing:** from the document's outer ancestors down toward the target.
2. **Target:** the element where the event occurred.
3. **Bubbling:** from the target back up through its ancestors.

The default <code>addEventListener()</code> setting listens during bubbling. Pass <code>{ capture: true }</code> to listen during capturing.

In an event handler, <code>event.target</code> is the element where the event began; <code>event.currentTarget</code> is the element whose listener is running. Pointer events also include coordinates: <code>offsetX</code>/<code>offsetY</code> are relative to the event target, <code>clientX</code>/<code>clientY</code> to the viewport, and <code>pageX</code>/<code>pageY</code> to the document. <code>stopPropagation()</code> prevents the event moving to other elements but lets other listeners on the current element run. <code>stopImmediatePropagation()</code> also stops later listeners on that same element. <code>preventDefault()</code> cancels the browser's default action, such as following a link, but does not stop propagation.

## 6. From Callbacks to Promises and <code>async</code>/<code>await</code>

A callback-based API gives another function control over when the callback runs. If dependent asynchronous steps are nested, the code can become difficult to read and maintain. When a callback is passed to a third-party library, its contract determines whether the callback runs, when it runs, how many times it runs, and what arguments it receives.

A Promise represents the eventual result of an asynchronous operation. It starts as **pending** and then settles as **fulfilled** or **rejected**. Only its first settlement takes effect; later calls to <code>resolve</code> or <code>reject</code> cannot change that outcome. A Promise is like a receipt for the result: callers attach <code>.then()</code>, <code>.catch()</code>, or <code>.finally()</code> handlers instead of relying on a third-party library to call the same callback correctly.

~~~js
function work(title, delay) {
  return new Promise(function (resolve) {
    setTimeout(function () {
      resolve(title);
    }, delay);
  });
}

work("A task", 500)
  .then(function (result) {
    console.log(result);
    return work("Next task", 300);
  })
  .then(function (result) {
    console.log(result);
  })
  .catch(function (error) {
    console.error(error);
  });
~~~

<code>async</code>/<code>await</code> uses Promises while making dependent steps read from top to bottom. An <code>async</code> function always returns a Promise. <code>await</code> pauses that function's continuation until the Promise settles; it does not block the browser's main thread.

~~~js
async function execute() {
  const user = await getUser();
  const preferences = await getPreferences(user.id);
  await updateDashboard(user, preferences);
}
~~~

## 7. AJAX and the Fetch API

AJAX describes requesting data and updating part of a page without a full reload. The name includes XML for historical reasons; the response can be JSON, text, or another format. <code>fetch()</code> is a modern Promise-based API for making these requests.

A <code>fetch()</code> call fulfills with a <code>Response</code> when the server responds, including for HTTP errors such as 404. Check <code>response.ok</code>, then read the body with <code>response.json()</code> or <code>response.text()</code>. Those body-reading methods are asynchronous too. The demo requests one JSON record and writes it as text rather than treating remote data as HTML.
