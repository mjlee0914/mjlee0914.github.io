## 다음 프로젝트에서 먼저 정하면 좋을 것

우리 팀은 첫 회의부터 디자인부터 했는데, 다음부터 정하면 좋을 것:

- 어떤 데이터가 어디로 흐르는지 먼저 정하고, 그 데이터를 받아 처리하는 페이지를 만든 뒤 화면에 배치하기

쇼핑몰 상품 목록 예시:

1. 필요한 데이터와 흐름 정하기: 상품 DB → 상품 API → 상품 목록 페이지
2. API가 어떤 모양의 데이터를 줄지 합의하기: 상품 이름, 가격, 이미지 주소 등
3. mock data 및 실제 웹 reference를 참고해 데이터를 받아 표시하는 페이지 만들기
4. 그 데이터가 카드나 상세 정보 중 어디에 들어갈지 정하고 디자인 다듬기
5. 백엔드와 연결해 실제 데이터로 확인하기

즉, **데이터 흐름과 API 약속은 먼저 정하고 백엔드·프론트엔드는 함께 진행할 수 있음.**

## User funnel

- 사용자가 원하는 목표, 예를 들면 **상품 구매**까지 어떤 단계를 거치는지 정리하는 방법
- 위에서 아래로 내려갈수록 일부 사용자가 다음 단계로 넘어가지 않아, 깔때기처럼 보여서 퍼널이라고 불림.

1. 메인 페이지
2. 상품 목록 보기
3. 상품 선택 → 상품 상세 보기
4. 장바구니 담기 → 장바구니 확인
5. 주문서 작성
6. 결제하기
7. 구매 완료

| 단계 | 사용자가 하는 일 | 페이지가 보여주거나 처리할 데이터 |
| --- | --- | --- |
| 상품 목록 | 상품을 둘러봄 | 상품명, 가격, 이미지 |
| 상품 상세 | 살 상품을 선택함 | 상품 설명, 옵션, 재고 |
| 장바구니 | 상품과 수량을 확인함 | 선택한 상품, 수량, 합계 |
| 주문서 | 배송 정보를 입력함 | 받는 사람, 주소, 주문 상품 |
| 결제 | 결제를 진행함 | 결제 금액, 결제 상태 |

- 실제로 분석할 때는 단계별 사용자 수를 봄
- 예를 들어 **상품 상세를 본 100명 중 20명만 장바구니에 담았다면**, 상품 정보나 가격, 구매 버튼에서 망설이는 이유가 있는지 살펴볼 수 있음
- 다만 퍼널은 보통 구매처럼 **하나의 목표까지 이어지는 큰 흐름**을 보여줌.
- 뒤로 가기, 로그인 요청, 재고 없음, 결제 실패 같은 갈림길까지 자세히 그리려면 사용자 흐름도도 함께 만들면 좋음.
- 주문서로 넘어가는 행동과 실제 결제 행동은 퍼널에서 따로 나누어 두면 각 단계가 명확해짐.
- 팀 작업 순서로 정리하면: **구매 목표 정하기 → 사용자 행동 단계 적기 → 단계별 필요한 데이터와 페이지 정하기 → 예외 상황과 갈림길 추가하기 → 화면 디자인하기**
- 나중에 실제 런칭까지 기획하는 웹페이지를 만들 때 과정으로 참고하면 좋을 듯!!

## `global-not-found.tsx`

```text
app/
├─ (shop)/
│  ├─ layout.tsx
│  ├─ not-found.tsx
│  └─ products/[id]/page.tsx
├─ admin/
│  ├─ layout.tsx
│  ├─ not-found.tsx
│  └─ products/page.tsx
└─ global-not-found.tsx
```

- `not-found.tsx`는 해당 라우트 안에서 `notFound()`가 호출됐을 때 가장 가까운 경로 구간의 404 화면을 보여줌. 예를 들어 상품 상세 페이지에서 상품이 없으면 쇼핑몰의 `not-found.tsx`가 사용됨.
- `global-not-found.tsx`는 어떤 라우트에도 매칭되지 않은 URL에 쓰는 전역 404 화면임. **experimental 기능이라** `next.config.ts`에서 `experimental.globalNotFound: true`를 켜야 함.
- `global-not-found.tsx`는 일반 layout을 거치지 않으므로 필요한 스타일을 직접 불러와야 하고, `<html>`과 `<body>`를 포함한 전체 문서를 반환해야 함.
- 여러 root layout이 있으면 각 layout에 공통으로 감싸지는 전역 404 화면을 만들기 어려워 `global-not-found.tsx`가 유용할 수 있음.

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: {
    globalNotFound: true,
  },
};

export default nextConfig;
```

### `/search`가 404가 되는 경우

- `app/(shop)/search/page.tsx`가 있고 그 안에서 `notFound()`를 호출하면 쇼핑몰의 `not-found.tsx`가 사용됨.
- `search/page.tsx`가 없고 catch-all도 없다면 `/search`는 매칭되지 않은 URL이므로 `global-not-found.tsx`가 켜져 있을 때 전역 404 화면으로 감. 이 설명은 **catch-all 라우트가 없다는 전제**임.
- 전역 404 기능을 켜지 않았다면 루트의 `app/not-found.tsx`가 매칭되지 않은 주소를 처리할 수 있음.
- `notFound()`는 해당 라우트를 그리는 중 호출해야 함. 이 함수는 실행을 중단하고 404 화면으로 넘김.

## `[...slugs]`

- **현재 경로 아래 남은 한 개 이상의 URL 구간을 전부 받는 catch-all 라우트**
- 받은 값은 배열로 전달됨.
- `app/(shop)/[...slugs]/page.tsx`가 있으면 `(shop)`은 URL에 나타나지 않으므로 `/search`도 이 라우트에 매칭됨.

```text
/search       → slugs: ["search"]
/abc/def      → slugs: ["abc", "def"]
```

- `[...slugs]`는 구간이 한 개 이상 있어야 매칭됨. 부모 경로 자체도 매칭하려면 `[[...slugs]]`처럼 optional catch-all을 사용함.
- `(shop)`은 URL 경로가 아니라 정리용 route group임. 그래서 이 catch-all은 쇼핑몰 URL만 받는다고 보장할 수 없음. `/admin/typo`처럼 더 구체적인 라우트가 없는 경로도 잡을 수 있으므로 팀에서 원하는 동작인지 정해야 함.
- catch-all이 `/search`를 이미 받아 처리하고 있으면 그 요청은 “어떤 라우트에도 매칭되지 않은 주소”가 아님. 해당 페이지에서 `notFound()`를 호출하면 일반적으로 가까운 `not-found.tsx`가 사용됨.

## `<Suspense>`

React의 비동기 렌더링과 관련된 컴포넌트. 비동기 작업을 직접 실행하는 게 아니라, 자식 컴포넌트가 아직 준비되지 않아 렌더링을 잠시 멈추면 보여줄 대체 UI를 지정함.

```tsx
<Suspense fallback={<div>Loading...</div>}>
  <Swiper>
    <SwiperSlide>이벤트 배너 1</SwiperSlide>
    <SwiperSlide>이벤트 배너 2</SwiperSlide>
  </Swiper>
</Suspense>
```

- 자식 컴포넌트가 실제로 suspend할 때 가장 가까운 `Suspense`의 `fallback`이 보임.
- 위 예시처럼 `Swiper`가 일반적으로 동기 렌더링만 하면 로딩 화면이 자동으로 나오지는 않음. 자식 컴포넌트나 사용하는 프레임워크가 Suspense를 지원하는 비동기 작업을 해야 함.

## DB에서 고객·관리자 기능 나누기

- 보통 고객과 관리자가 하나의 DB를 공유하고, 상품 테이블도 함께 사용할 수 있음.
- 기능을 권한에 따라 나눔: 고객은 판매 중인 상품을 보고 주문하고, 관리자는 상품을 추가·수정·삭제할 수 있음.
- 같은 조회 로직은 조건, 권한, 보이는 데이터 범위가 같을 때 공통 함수로 재사용할 수 있음. 고객용 조회와 관리자용 조회는 보이는 상품 범위가 다를 수 있으므로 권한에 따라 나누는 것 조심.
- 화면에서 버튼을 숨기는 것만으로 권한이 보호되지는 않음. 요청을 처리하는 서버/API와 DB에서도 사용자의 권한을 확인해야 함.

```text
고객 화면 → 상품 조회·주문 기능 ─┐
                                ├→ 같은 DB
관리자 화면 → 상품 조회·관리 기능 ┘
                 ↑
       공통 권한 확인 로직
```
