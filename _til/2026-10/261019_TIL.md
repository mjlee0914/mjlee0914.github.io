## Supabase clients

Install the base Supabase client and the SSR helpers:

```bash
npm install @supabase/supabase-js @supabase/ssr
```

- `@supabase/supabase-js` provides the core client for database and authentication features.
- `@supabase/ssr` helps configure browser and server clients that store Supabase Auth sessions in cookies, so both sides can work with the user's session.

The project keeps its Supabase client setup in `shared/lib/supabase.ts`.

## Environment variables in Next.js

Environment variables are read with `process.env`. Files such as `.env`, `.env.development`, `.env.production`, and `.env.local` let a project use different values in different environments. `.env.local` is commonly used for machine-specific values and should not be committed when it contains secrets.

Next.js checks for each variable in this order, stopping at the first match:

1. `process.env`
2. `.env.$(NODE_ENV).local`
3. `.env.local` (skipped when `NODE_ENV` is `test`)
4. `.env.$(NODE_ENV)`
5. `.env`

For example, `.env.development` is used in development and `.env.production` in production. `NEXT_PUBLIC_` marks a value for inclusion in browser JavaScript, so it can be read by client code as well as server code. These public values are embedded during the build and must not contain secrets. Variables without this prefix stay server-side.

## Client and server code

A browser sends a request to the Next.js server. The server can read data from Supabase and send a response back for the browser to display.

```text
Browser form → Next.js Server Action → Supabase Auth or database
Browser UI  ← action result and updated state ← Next.js server
```

- `'use client'` marks a client entry point for features such as React state, event handlers, and browser APIs. Client Components can still be rendered into initial HTML on the server; the directive defines the client boundary.
- `'use server'` marks a server function. A file-level directive makes its exported functions server functions, which can be imported into a Client Component and connected to a form.
- Server actions still need input validation and appropriate authentication and authorization checks.

## Forms, `FormData`, and `useActionState`

When a user submits a form, the browser's `FormData` carries the submitted fields to the action. A Server Action can validate that data, perform work such as signing up a user, and return a result for the UI to show.

```ts
export interface ActionState<T = unknown> {
  success: boolean;
  message?: string;
  errors?: Record<string, string>;
  data?: T;
}

export const INITIAL_ACTION_STATE: ActionState = {
  success: false,
};
```

`useActionState` is used in a Client Component. It connects an action to a form and keeps the latest returned state:

```tsx
const [state, formAction, isPending] = useActionState(
  signUpAction,
  INITIAL_ACTION_STATE,
);
```

Here, `state` is the action's latest result, `formAction` is passed to the form's `action` prop, and `isPending` indicates that submission is in progress. When used with this hook, the action receives the previous state and the submitted form data.

## API design is data transfer

An API describes how one part of an application requests data or an operation from another. A RESTful API organizes endpoints around resources and uses HTTP methods to describe common operations:

- `GET` reads a resource.
- `POST` creates a resource or submits an operation.
- `PATCH` updates part of a resource.
- `DELETE` removes a resource.

An API specification should make the agreement concrete: the route and method, the input fields, the response shape, possible errors, and any authentication requirements. For a product-list page, for example, the frontend and backend need to agree on which product fields the endpoint returns before building the UI around them.
