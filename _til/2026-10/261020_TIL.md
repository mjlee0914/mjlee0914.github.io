## 체크아웃 배송지 정보 흐름

오늘 체크아웃 배송지 기능을 구현하며 컴포넌트, Server Action, query 함수, Supabase가 어떻게 이어지는지 정리했다.

### 최근 결제 완료 주문의 배송지 불러오기

`ShippingInfo` Client Component에서 **배송정보 불러오기** 버튼을 누르면 Server Action이 실행된다. Action은 서버용 Supabase 클라이언트를 만들고 `supabase.auth.getUser()`로 현재 로그인 사용자를 확인한다. 확인된 사용자의 ID를 query 함수에 전달해 해당 사용자의 주문만 조회한다.

Query는 `orders`에서 배송지 6개 필드를 선택하고, 외래 키로 연결된 `payments` 정보를 함께 조회한다. 결제 상태가 `DONE`인 주문만 남긴 뒤 `created_at` 최신순으로 정렬하고, `maybeSingle()`로 최대 한 건을 가져온다.

```text
배송정보 불러오기 버튼 클릭
  → ShippingInfo에서 Server Action 호출
  → Action에서 로그인 사용자 확인
  → Query에서 해당 사용자의 최근 결제 완료 주문 조회
  → Action이 화면에서 사용할 결과 반환
  → Component가 state를 갱신하고 배송지 표시
```

조회 결과에는 `recipient`, `recipient_phone`, `zipcode`, `address`, `address_detail`, `delivery_memo`가 포함된다.

Action은 결과에 따라 다음처럼 처리한다.

- **로그인 사용자 없음:** `success: false`와 세션 안내 메시지를 반환한다.
- **조건에 맞는 결제 완료 주문 없음:** 조회 자체는 성공했으므로 `success: true`, `data: null`을 반환한다.
- **Query 오류:** Query에서 오류를 던지고 Action의 `catch`에서 사용자용 오류 메시지로 바꿔 반환한다.
- **배송지 조회 성공:** 배송지 데이터를 반환하고 Component가 각 입력 state를 갱신한다.

### 작성 순서와 실행 순서

데이터 기능은 작성할 때의 의존 순서와 사용자가 실행할 때의 순서가 다르다. 새 기능을 만들 때는 결과 타입을 먼저 정하고 Query, Server Action, Component 순으로 연결하면 각 계층의 역할을 나누기 쉽다.

```text
작성:   타입 → Query → Server Action → 컴포넌트
실행:   컴포넌트 → Server Action → Query → Supabase
응답:   Supabase → Query → Server Action → 컴포넌트
```

기존 `ShippingInfo` 화면이 먼저 만들어져 있어 실제 작업에서는 컴포넌트를 먼저 살펴봤다. 이후 의존 관계를 따라가며 전체 데이터 흐름을 정리하니 각 함수의 역할을 설명하기 쉬워졌다.

### 배송 요청사항 state 구분

배송 요청사항은 서로 연결된 두 state로 관리한다.

- `deliveryMemoOption`: 드롭다운에서 선택한 값(`door`, `call`, `security`, `postbox`, `direct`)을 저장한다.
- `deliveryMemo`: 주문 제출에 사용할 최종 문구를 저장한다.

기본 항목을 고르면 선택 값에 맞는 문구를 찾아 `deliveryMemo`에 저장한다. **직접 입력**을 고르면 입력창을 표시하고, 사용자가 작성한 문구를 `deliveryMemo`에 저장한다. 숨김 `input` 요소는 이 최종 문구를 폼 제출값으로 보관한다.

최근 배송지를 불러올 때는 저장된 문구가 기본 항목의 문구와 같은지 확인한다. 일치하면 해당 드롭다운 항목을 선택하고, 목록에 없는 문구라면 **직접 입력**을 선택해 기존 문구를 입력창에 복원한다.

### Kakao 우편번호 검색

Next.js `Script`의 `afterInteractive` 전략으로 Kakao 우편번호 스크립트를 불러온다. 사용자가 검색 결과를 선택하면 `data.zonecode`에서 우편번호를 가져오고, `userSelectedType`이 `R`이면 도로명 주소를, `J`이면 지번 주소를 사용한다. 우편번호와 주소 state를 갱신한 뒤, 새 주소에 맞는 상세주소를 다시 입력하도록 기존 상세주소를 비운다.

## 다음에 점검할 내용

- `ShippingInfo`를 위에서 아래까지 읽으며 각 state와 이벤트 함수의 역할 설명하기
- 로그인 사용자와 `DONE` 결제 내역이 있는 테스트 데이터로 최근 배송지 조회하기
- 결제 완료 주문이 없을 때 안내가 표시되는지 확인하기
- 기본 배송 요청사항과 직접 입력 문구가 각각 복원되는지 확인하기
- 도로명·지번 주소 선택, 주소 재선택 시 상세주소 초기화 확인하기
- 상세주소 오류가 입력 전부터 표시되는 문제를 점검하고, 우편번호·주소 입력란을 `readOnly`로 할지 검토하기
- 주소 선택 후 상세주소 입력란에 자동으로 포커스를 이동할지 검토하고 개발용 `console.log` 및 ESLint 확인하기

Toss 결제를 연결하기 전에는 장바구니 데이터 구조와 최종 결제 금액이 준비되어야 한다. 다음 구현은 주문 상품 표시, 상품 금액과 배송비 계산, 주문 생성, 결제 요청 순서로 진행하는 것이 자연스럽다. 결제 위젯 표시 준비는 앞서 할 수 있지만, 실제 결제 요청에는 주문 ID와 확정된 최종 금액이 필요하다.

## 회고

기능을 이해할 때 각 계층이 맡은 역할을 나누어 보는 것이 도움이 됐다. 컴포넌트는 입력과 화면 표시를 관리하고, Server Action은 로그인 사용자를 확인한 뒤 화면에 전달할 결과를 만들며, Query 함수는 주문 데이터를 조회한다. 결제 기능으로 넘어가기 전에 이 흐름을 내 말로 설명할 수 있도록 한 번 더 점검하고 싶다.
