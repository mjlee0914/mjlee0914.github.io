## 회원가입 폼: 라우팅과 실행 시점

### `useRouter`: App Router와 Pages Router

`next/navigation`과 `next/router`의 차이는 **CSR과 SSR의 차이가 아니라 라우터 종류의 차이**다. App Router의 Client Component에서는 `next/navigation`의 `useRouter`를, Pages Router에서는 `next/router`의 `useRouter`를 사용한다. 둘 다 전체 문서를 다시 여는 대신 Next.js가 화면을 전환하는 클라이언트 측 내비게이션에 쓴다. 일반 링크 이동에는 보통 `<Link>`를 사용한다.

- `router.push('/path')`: 새 방문 기록을 추가한다. 뒤로 가기로 이전 페이지에 돌아갈 수 있다.
- `router.replace('/path')`: 현재 방문 기록을 목적지로 바꾼다. 회원가입 성공 뒤 로그인 화면으로 돌아가지 않게 할 때 쓸 수 있다.
- `router.refresh()`: 현재 경로의 Server Component 데이터를 다시 요청해 화면을 갱신한다. 브라우저 전체 새로고침과 다르고, 서버의 지속 캐시를 무효화하지도 않는다.

회원가입 성공 결과를 받은 뒤 이동하는 간단한 예시다.

```tsx
useEffect(() => {
    if (!state.success) return;

    alert(state.message);
    router.replace('/');
}, [state.success, state.message, router]);
```

목적지로 이동하는 경우에는 보통 `replace`만으로 충분하다. `refresh`는 같은 경로의 서버 데이터를 다시 가져와야 할 때 사용한다.

### Effect 훅은 언제 쓸까?

React Effect는 DOM 반영 후 타이머, 브라우저 이벤트, 외부 위젯처럼 React가 관리하지 않는 시스템과 동기화할 때 쓴다. 다른 state에서 계산할 수 있는 값은 Effect로 복사하지 않고 렌더링 중 계산한다.

| 훅 | 시점과 주 용도 |
| --- | --- |
| `useEffect` | DOM 반영 뒤 실행된다. 대개 화면이 그려진 뒤 외부 시스템을 연결하거나 데이터를 동기화한다. |
| `useLayoutEffect` | DOM 반영 뒤, 브라우저가 그리기 전에 실행된다. 툴팁 위치처럼 크기를 재고 즉시 보정해야 할 때 쓴다. 화면 그리기를 막으므로 꼭 필요할 때만 쓴다. |
| `useInsertionEffect` | 레이아웃 Effect보다 먼저 스타일을 삽입할 수 있다. 주로 CSS-in-JS 라이브러리용이며 일반 컴포넌트 로직에는 거의 쓰지 않는다. |

의존성 배열을 생략하면 커밋마다, `[]`는 마운트 시, `[a, b]`는 처음과 `a` 또는 `b`가 바뀐 뒤 실행된다. Effect에서 읽는 props와 state는 의존성에 포함한다. 이벤트 구독은 반환하는 정리 함수에서 해제한다. 개발용 Strict Mode는 설정·정리를 한 번 더 확인할 수 있어 `[]`도 개발 중 “무조건 한 번”을 뜻하지 않는다.

Next.js에서는 데이터 조회를 Server Component에서 처리할 수 있는지 먼저 본다. Effect 콜백 자체는 `async`로 만들지 않고, 필요하면 내부에서 비동기 함수를 호출한다.

### `useRef`와 사용자 정의 폼 훅

`useRef`는 렌더링 결과에 직접 쓰지 않는 값을 보관하거나 DOM 요소에 접근할 때 쓴다. `ref.current`를 바꿔도 리렌더링되지 않는 점이 `useState`와 다르다. 예를 들어 주소 선택 뒤 상세주소 입력란에 포커스를 주거나 타이머 ID를 저장할 수 있다.

프로젝트의 `useFormState<T>`는 `useState`와 공통 `onChange` 함수를 묶어 `[form, onChange]`를 돌려주는 사용자 정의 훅이다. 입력 요소의 `name`을 객체의 키로 사용해 해당 필드만 갱신한다. JSX를 반환하지 않고 입력 상태와 핸들러만 제공하므로 `.ts` 파일에 둘 수 있다. Hook을 사용하는 컴포넌트이므로 `useFormState`처럼 `use`로 시작하고 컴포넌트나 다른 Hook의 최상위에서 호출한다.

`import type { UserProfile } from '...'`와 `import { type UserProfile } from '...'`는 둘 다 유효한 타입 전용 import 문법이며, 타입 참조는 JavaScript 출력에 포함되지 않는다.

## 로그인 사용자, 쿠키, `cache()`

`getCurrentUser()`는 쿠키를 사용하는 서버용 Supabase 클라이언트로 `supabase.auth.getUser()`를 호출한다. `getUser()`는 Auth 서버에 요청해 사용자를 검증한다. 이후 `profiles`에서 ID가 일치하고 `deleted_at`이 `null`인 프로필을 찾는다. 사용자나 프로필이 없으면 `null`, 있으면 필요한 필드를 `UserProfile` 모양으로 반환한다.

React의 `cache()`는 Server Component 요청 안에서 같은 함수가 같은 인자로 다시 불리면 결과를 재사용하는 메모이제이션이다. 인자가 없는 `getCurrentUser()`는 그 요청 안의 중복 Supabase 조회를 줄인다. 요청이 끝나면 캐시도 끝나므로 사용자 간에 공유되지 않는다. 사용자 100명의 요청을 하나로 합치는 기능은 아니다.

| 구분 | 쿠키 | React `cache()` |
| --- | --- | --- |
| 역할 | 로그인 세션 정보를 다음 요청에도 전달 | 같은 서버 렌더링 요청 안의 중복 계산을 줄임 |
| 범위·수명 | 만료 또는 세션 종료까지 요청과 함께 전달 | 현재 서버 요청 동안만 유지 |

흐름: **브라우저가 세션 쿠키 전송 → 서버 클라이언트가 로그인 사용자 확인 → 같은 요청에서 재호출하면 `cache()`가 결과 재사용.** 쿠키는 요청 간 세션을 전달하고, `cache()`는 한 요청 안의 반복 작업을 줄인다.

`'use server'`는 파일에 두면 해당 파일의 내보낸 함수를 Server Function으로 표시한다. 단순히 “이 파일은 서버에서만 실행된다”는 주석과 같지는 않으므로, UI에서 호출할 서버 함수인지 서버 내부 조회 도우미인지 구분해서 이해한다.

## URL 검색값과 React `use()`

- App Router의 `useSearchParams()`는 Client Component에서 쿼리 문자열을 읽는다. `/sign-up?next=/dashboard`의 `searchParams.get('next')`는 `/dashboard`를 반환한다. 서버 페이지는 `searchParams` prop을 쓸 수 있다.
- React `use(promise)`는 Promise의 값을 읽고, 대기 중이면 가까운 `<Suspense>`의 대체 화면을 보여준다. 서버에서는 보통 `await`를 쓰며, Client Component에서 서버가 전달한 Promise를 읽을 때 `use()`를 활용한다.

## 체크아웃 배송지 기능 복습

`ShippingInfo`의 버튼은 Server Action을 호출한다. Action은 로그인 사용자의 ID를 Query에 전달하고, Query는 해당 사용자의 `orders` 중 `payments.status = 'DONE'`인 주문을 최신순으로 한 건 조회한다. 결과는 받는 사람·연락처·우편번호·주소·상세주소·배송 요청사항이다.

```text
작성: 타입 → Query → Server Action → 컴포넌트
실행: 컴포넌트 → Server Action → Query → Supabase → 컴포넌트 상태 갱신
```

로그인 사용자가 없으면 실패 결과를, 결제 완료 주문이 없으면 `success: true`, `data: null`을 반환한다. 배송 요청사항은 선택값 `deliveryMemoOption`과 제출할 문구 `deliveryMemo`를 구분한다. 이전 문구가 기본 목록에 없으면 직접 입력으로 복원한다. Kakao 검색은 `R`이면 도로명, `J`이면 지번 주소를 선택하고 새 주소를 고르면 상세주소를 비운다.
