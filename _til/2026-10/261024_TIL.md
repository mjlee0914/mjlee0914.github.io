# 웹기초

## 프로젝트 발표 피드백

- 발표 첫 부분에서 **어떤 문제를 해결했는지** 보여주면 관심을 끌기 좋다.
- **문제 → 해결 방법 → 달라진 결과** 순서로 설명한다.

```text
문제
→ 댓글 작성 때마다 전체 페이지가 새로고침됨.

해결
→ Ajax로 댓글을 전송하고 목록만 갱신.

결과
→ 페이지 전체를 다시 불러오지 않고 댓글 확인.
```

- [프로젝트 발표 PPT](https://docs.google.com/presentation/d/1W6LVvYJaRfGo2mhWDVaqMYNADKjFyb9HRm3XAZGlNZw/edit?usp=drivesdk)

---

- client: 서비스를 **요청**하는 쪽. 주로 브라우저.
- server: 요청을 받아 처리하고 결과를 **돌려주는** 프로그램 혹은 컴퓨터
- Request: ex) "이것을 주세요", "이것을 저장해 주세요."
- Response: ex) "여기 있습니다", "저장했습니다", "찾을 수 없습니다"
- Resource: ex) 요청할 수 있는 대상. ex) HTML, CSS, 사진, 게시글 데이터 등
- URL: 그 자원이 어디 있는지 가르키는 주소

```

client -- **request** --> server
server -- **response --> client
```

```
예시

① 브라우저: 페이지의 HTML을 주세요.
② 서버: HTML을 보내줄게요.

③ 브라우저: HTML을 읽어보니 CSS와 사진도 필요하네?
④ 브라우저: CSS를 주세요. 사진도 주세요.
⑤ 서버: 각각 보내줄게요.

⑥ 브라우저: 받은 내용을 조립해서 화면을 보여줌.

```

- 한 페이지가 여러 자원을 사용한다.
- 그래서 개발자 도구의 Network 탭에서는 여러 요청이 보인다.

## Protocol이란?

우선 데이터를 보낼 때 다음과 같은 약속이 필요하다.

- 어디에 요청?
- 무엇을 ?
- 어떤 형식의 데이터?
- 어떻게 처리 결과를 받을지?

이런 통신 규칙이 바로 **protocol** 이다.

## HTTP와 HTTPS

- HTTP: 웹에서 요청과 응답을 주고받을 때 사용하는 통신 규칙
- HTTPS: HTTP 통신을 암호화해서 주고받는 방식
  - 암호화: 중간에서 내용을 보더라도 쉽게 알아볼 수 없도록 바꾸는 것

```
HTTP 규칙에 맞춰 클라이언트가 요청 -> 서버가 HTTP 규칙에 맞춰 응답
```

---

## HTTP 메시지

- 메시지: 클라이언트와 서버가 주고 받는 정보
- 전문: 메시지 전체
  - 요청 전문과 응답 전문
  - 크게 첫 줄, Header, body로 구분함.
  - body는 없는 경우도 있음.

주의:

- **요청** 전문 **첫 줄**: GET, POST 같은 메서드
- **응답** 전문 **첫 줄** : 200, 404 같은 **_상태 코드_**

Content-Type

- 지금 보내는 내용이 어떤 형식인지 알려주는 표시
- 요청과 응답 양쪽에서 사용 가능

```http
Content-Type example

text/html : html 문서
application/json: JSON 데이터
application/x-www-form-urlencoded: 이름=값&이름=값 형태의 폼 데이터
multipart/form-data: 파일 업로드 등에 사용하는 폼 데이터
image/png: PNG 이미지

```

### 요청 전문

```http
요청 전문 예시)

POST /posts HTTP/1.1
Host: example.com
Content-Type: application/json

{"subject":"HTTP 공부"}

```

- 첫 줄: 요청 메서드 (POST), 요청 경로(/posts), HTTP 버전(HTTP/1.1)
- Header: 요청에 관한 추가 설명
- 빈 줄: Header와 Body를 구분함.
- Body(본문): 서버로 보내는 실제 데이터

### 응답 전문

```http
응답 전문 예시)

HTTP/1.1 201 Created
Content-Type: application/json

{"id":1,"subject":"HTTP 공부"}

```

- 첫 줄: HTTP 버전과 처리 결과
- Header: 응답 데이터의 형식 등 추가 설명
- Body: 서버가 돌려준 실제 내용
- 응답 Body에는 HTML, JSON, 이미지 등이 들어갈 수 있음.

## 주요 요청 Header

User-Agent

- 요청을 보낸 프로그램에 관한 정보
- 브라우저와 운영체제 등을 "추측" - 실제 사용자 기기나 운영체제 버전을 정확히 보장하지는 않음

Accept

- 어떤 형식의 응답을 받을 수 있는지 알려줌

```html
Accept: text/html,application/xml;q=0.9,*/*;q=0.8
```

- `*/*`: 모든 형식
- `q`: 선호도 - 값이 클수록 더 선호. 생략될 시 기본값 1.

Accept-Encoding

```html
Accept-Encoding: gzip, deflate, br, zstd
```

- 받아서 풀 수 있는 압축 방식을 알림
- 서버는 지원되는 방식으로 내용을 압축해 보내기 가능
- URL encoding과는 다른 의미임

Accept-Language

```html
Accept-Language: en-GB,en-US;q=0.9,en;q=0.8
```

- 선호하는 응답 언어
- 서버가 참고만 함.

## Request Method

- 서버에 "무엇을" 해 달라는지 나타냄
- 실제 처리는 서버에 작성된 코드가 담당함

```
Request Methods

GET: 조회 / 게시글 읽기
POST: 보낸 데이터 처리 / 게시글 등록
PUT: 대상 전체 교체 / 게시글 전체 교체
PATCH: 일부 수정 / 제목만 수정
DELETE: 삭제 / 게시글 삭제
HEAD: GET과 같은 응답에서 body 제외 / 파일 정보 확인
OPTIONS: 통신 옵션 확인 / CORS 사전 확인

```

GET

- 자원을 조회할 때
  - HTML, image, JSON 등 조회 가능
  - 일반적인 GET 요청은 body 없이 사용함
  - 일례로 검색 조건은 주로 url에 넣음 -> GET 요청의 Content-Type은 보통 필요 없음

POST

- 데이터를 보내 서버가 처리하도록 요청함
- 새 게시글 생성, 로그인 처리 등에 사용함
- 항상 새 자원 생성만 의미하는 것은 아님

DELETE

- ex) `DELETE /posts/3` : 3번 게시글 삭제 요청

HEAD

- GET처럼 요청하되 응답 body를 받지 않고 header 정보만 받아올 때 사용
- 실제 내용을 다운로드 하지 않고 관련 정보를 확인할 때 사용 (읽기 전용 메서드)

## URL, Query String, Search Params

```
https://example.com/search?subject=HTTP&page=2
```

- https : 사용하는 통신 방식
- example.com :사이트 도메인 이름
- /search : 요청할 대상의 경로
- ? : 추가 조건이 시작되는 표시
- subject=HTTP : subject라는 이름으로 HTTP 전달
- & : 여러 조건을 연결
- page=2 : page라는 이름으로 2 전달

Query string

- ? 뒤에 붙는 문자열

Search params

- URL에 들어 있는 검색 매개변수들
- 검색어 뿐만 아니라 페이지 번호, 정렬 기준, 카테고리 등도 매개변수에 전달 가능

```
?category=shoes&sort=price
```

- 신발 카테고리를 가격 기준으로 조회

## payload, URL encoding

payload

- 요청으로 전달하는 실제 데이터
- 개발자 도구에서는 전달 형식에 따라 구분해서 보여줌
  - ex) Query String Parameters - url에 붙인 조건
  - form data - 폼 형식으로 보낸 데이터
  - request payload - JSON 등으로 보낸 요청 데이터

URL encoding

- 문자를 URL에서 다룰 수 있는 형태로 표현하는 규칙 (컴퓨터 언어로 바뀌는 것 보다는)
- `%`와 16진수 등으로 표현

```
URL encoding example

안녕 -> %EC%95%88%EB%85%95
```

- 폼 형식에서 공백은 `+`로 표현
- 암호화가 아님 -> 원래 문자로 되돌릴 수 있음

## Stateless (무상태성)

- HTTP는 이전 요청의 사용자 상태를 자동으로 이어서 기억하지 않음
- 각각의 요청을 독립적으로 처리함
- but 서버가 데이터를 저장할 수 없다는 뜻은 아님

```
ex)
첫 요청: 로그인할게요.
다음 요청: 내 장바구니를 보여주세요.

→ HTTP만으로는 두 요청이 같은 사용자의 요청인지 자동 연결되지 않음.
```

- -> 로그인 상태 등을 이어서 관리하려면 cookie, session 같은 방법을 사용함.

### cookie

- 브라우저에 저장하는 작은 데이터
- 로그인 유지, 언어 설정, 사용자 추적 등에 사용함.
- 브라우저는 저장된 쿠키를 조건에 맞는 "요청"에 함께 보냄

Set-Cookie

- 서버 -> 브라우저. 쿠키 저장을 위한 정보 전달

Cookie

- 브라우저 -> 서버. 저장된 쿠키를 요청에 함께 전달

```
① 브라우저 → 서버: 로그인 요청

② 서버 → 브라우저:
   Set-Cookie: sessionId=abc123

③ 브라우저: 쿠키 저장

④ 브라우저 → 서버: 장바구니 요청
   Cookie: sessionId=abc123

⑤ 서버: 세션 번호로 사용자를 확인하고 장바구니 응답
```

### session

- 여러 요청에 걸쳐서 사용자 상태를 "이어서" 관리함
- 대표적 예시: 서버가 세션 번호와 사용자 정보를 연결해서 저장함

```
ex)

브라우저의 쿠키
sessionId=abc123

서버의 세션 정보
abc123 → 로그인한 민지
```

## Origin과 CORS

Origin

- 출처.
- 프로토콜 + 도메인 + 포트
- 세 가지 중 하나라도 다르면 다른 출처
- 포트: 같은 컴퓨터에서 어떤 서비스와 통신할지 구분하는 번호

```
http://localhost:3000
http://localhost:4000

→ 포트가 다르므로 다른 출처.
```

CORS

- 다른 출처의 응답을 브라우저의 JavaScript가 사용할 수 있도록, 서버가 허용 여부를 알려주는 방식.
- 서버의 응답 헤더를 보고 브라우저가 판단한다.
- 다른 출처의 모든 자원 이용이 무조건 금지된다는 뜻은 아니다.

Preflight: 사전 요청

- 일부 다른 출처 요청을 보내기 전에 허용 여부를 확인하는 과정.
- 브라우저가 OPTIONS 메서드로 확인한다.
- 모든 요청 전에 발생하는 것은 아니다.

```
브라우저 → 서버
OPTIONS: 이 출처에서 JSON을 POST해도 되나요?

서버 → 브라우저
허용한다는 헤더로 응답

브라우저 → 서버
실제 POST 요청

서버 → 브라우저
처리 결과와 필요한 CORS 헤더로 응답
```

- 사전 요청에서 허용되지 않으면 브라우저가 실제 요청을 보내지 않는다.
- 사전 요청 없이 전송되는 경우에는 요청이 서버에 도착해도 브라우저가 응답 사용을 막을 수 있다.
- 따라서 CORS 오류가 항상 “서버에 요청이 도착하지 않았다”는 뜻은 아니다.

## Status Code: 상태 코드

- 서버가 요청을 어떻게 처리했는지 알려주는 번호.
- HTTP/1.1 형식에서는 응답 첫 줄에 있다.

```
1xx: 처리 중간 안내
2xx: 성공
3xx: 이동, 기존 응답 재사용 등의 추가 처리
4xx: 요청 관련 문제
5xx: 서버 쪽 처리 문제
```

2xx: 성공

- 200 OK: 요청 처리 성공.
- 201 Created: 새 자원 생성 성공. POST에서 자주 사용.

3xx: 이동·재사용 등

- 301 Moved Permanently: 자원 주소가 영구적으로 바뀜.
- 302 Found: 일시적으로 다른 주소를 이용하도록 안내.
- 304 Not Modified: 내용이 바뀌지 않았으므로 저장된 것을 사용.

4xx: 요청 관련 문제

- 400 Bad Request: 잘못된 요청 형식 등으로 처리 불가.
- 401 Unauthorized: 유효한 인증 정보가 필요.
- 403 Forbidden: 접근 거부.
- 404 Not Found: 요청한 자원을 찾지 못함.

```
인증: 누구인지 확인.
권한: 무엇을 할 수 있는지.

401 → 인증 정보를 확인해야 함.
403 → 접근을 허용하지 않음.
```

- 4xx는 프론트엔드 코드나 설정 문제로도 발생 가능

5xx: 서버 문제

- 500 Internal Server Error: 서버에서 예상하지 못한 문제 발생.
- 502 Bad Gateway: 중간 서버가 뒤쪽 서버에서 잘못된 응답을 받음.
- 503 Service Unavailable: 과부하·점검 등으로 현재 서비스 제공이 어려움.

## Location과 Redirect

- Redirect(리다이렉트): 다른 주소로 안내하는 것.
- Location: 새 주소 등을 알려주는 응답 헤더.
- 상태 코드와 함께 해석해야 한다.

```
HTTP/1.1 301 Moved Permanently
Location: https://example.com/new
```

“주소가 영구적으로 바뀌었으니 새 주소를 이용하세요.”

- 301은 브라우저의 요청에도 응답할 수 있다.
- 서버끼리 통신할 때만 사용하는 코드가 아니다.

JavaScript로 요청했을 때

```
location.href = "/new"	브라우저가 새 페이지로 이동
fetch()가 리다이렉트를 만남	보통 새 주소로 요청을 이어가지만 화면 전체가 자동 이동하지는 않음
```

- 중요한 차이는 페이지 이동인지, 데이터 요청인지다.

## Cache와 304

- Cache(캐시): 받은 데이터를 나중에 다시 쓰기 위해 저장하는 것.
- 같은 파일을 매번 다운로드하지 않아서 속도와 통신량을 줄일 수 있다.

```
① 처음 요청
브라우저: style.css 주세요.
서버: 200 OK + CSS 내용
브라우저: CSS 저장

② 나중에 다시 확인
브라우저: 전에 받은 CSS가 바뀌었나요?
서버: 304 Not Modified
브라우저: 저장해 둔 CSS 사용
```

- 304는 오류가 아니다.
- Disable cache: 개발자 도구에서 브라우저 캐시 사용을 억제하는 기능.
- 다시 전체 내용을 받으면 200을 볼 수 있지만, 항상 200이 되는 것은 아니다.
- CSS·JS 수정이 안 보이는 원인이 항상 캐시인 것도 아니다.

## Network 탭에서 확인하는 정보

```
Request URL	요청한 주소
Request Method	GET, POST 같은 요청 방식
Status Code	처리 결과
Remote Address	연결한 상대의 IP 주소와 포트
Referrer Policy	출발 페이지 정보를 얼마나 전달할지 정하는 정책
```

```
Remote Address
223.130.200.219:443
```

- 노트에 기록한 당시의 연결 주소.
- IP 주소: 네트워크에서 통신 상대를 찾는 데 쓰는 주소.
- 443: HTTPS의 기본 포트.
- 연결 상대는 중간 서버일 수도 있다.

## Referrer Policy

- Referrer: 어느 페이지에서 넘어왔는지에 관한 정보.
- Referrer Policy: 그 정보를 얼마나 전달할지 정하는 정책.

`strict-origin-when-cross-origin`의 기본적인 동작:

- 같은 출처: 경로와 검색 조건까지 전달할 수 있음.
- 다른 출처: 보통 출처까지만 전달.
- HTTPS → HTTP: 전달하지 않음.

## Ajax와 CSR

Ajax

- 페이지 전체를 다시 불러오지 않고 서버와 통신하는 방식.
- 받은 데이터로 필요한 부분만 갱신할 수 있다.
- 보통 JavaScript의 fetch() 등을 사용한다.
- 이름에 XML이 들어가지만 JSON도 많이 사용한다.

```
  댓글 작성
  → 서버에 댓글 전송
  → 서버 응답
  → 댓글 목록 부분만 갱신
```

- 비동기: 요청 결과를 기다리는 동안 다른 작업도 진행할 수 있다는 뜻.

CSR

- Client-Side Rendering의 줄임말.
- 브라우저에서 JavaScript로 화면을 만드는 방식.
- Rendering(렌더링): 내용을 화면에 표시할 형태로 만드는 것.
  ```
  개념 초점
  Ajax 서버와 데이터를 어떻게 주고받는가
  CSR 화면을 어디에서 만드는가
  ```
- Ajax와 CSR은 같은 뜻이 아니다.
- 전체 새로고침이 없다고 반드시 React를 사용한 것은 아니다.
- 일반 <a> 링크는 페이지를 이동하지만, 앱에서 JavaScript로 처리하면 전체 문서를 다시 받지 않고 이동하기도 한다.

## Next.js의 Request와 Response

- Next.js에서도 HTTP 요청을 받고 응답을 보낸다.
- Request를 통해 실제로 전달된 정보를 확인할 수 있다.
- 사용자의 모든 환경을 자동으로 알 수 있는 것은 아니다.

```
Request에서 확인	Response에 담아 전달

URL과 검색 조건	상태 코드
메서드	응답 헤더
요청 헤더와 쿠키	쿠키 설정
요청 Body	HTML, JSON 등의 Body
```

```
Request
→ “제목이 HTTP인 게시글을 저장해 주세요.”

서버
→ 입력값 확인 → 저장

Response
→ 201 Created
→ 생성한 게시글 데이터
```

## 실제 웹의 HTTP 전체 흐름

사이트 접속 → 로그인 → 게시글 작성의 예시, 실제 서비스에서는 캐시나 로그인 방식 등에 따라 일부 과정이 달라질 수 있다.

① 주소 입력과 연결 준비

```
사용자: 주소창에 https://example.com 입력
```

- 브라우저가 통신할 상대를 찾는다.
- 필요한 연결을 준비한다.
- HTTPS에서는 암호화 통신도 준비한다.
- 기존 연결이 있으면 재사용할 수도 있다.

② 페이지 조회 요청

```
GET / HTTP/1.1
Host: example.com
Accept: text/html
Accept-Language: ko
```

```
브라우저 → 서버
“첫 화면을 주세요. HTML을 받을 수 있고 한국어를 선호해요.”
```

- GET으로 페이지를 조회한다.
- 일반적으로 요청 Body는 없다.

③ 서버의 HTML 응답

```
HTTP/1.1 200 OK
Content-Type: text/html
<html>...</html>
```

```
서버 → 브라우저
“성공했습니다. 내용은 HTML입니다.”
```

- 상태 코드는 처리 결과.
- Content-Type은 내용의 형식.
- Body는 실제 HTML.

④ 추가 자원 요청과 화면 표시

```
HTML 읽기
→ CSS, JavaScript, 이미지가 필요한 것을 확인
→ 필요한 자원들을 추가 요청
→ 각 응답을 받아 화면 구성
```

- 캐시된 자원은 재사용할 수도 있다.
- 변경 여부를 확인한 결과 304가 오면 저장된 내용을 사용한다.
- 이것이 Network 탭에 여러 요청이 보이는 이유다.

⑤ 로그인 요청

```
사용자: 아이디·비밀번호 입력 후 로그인 클릭

브라우저 → 서버
POST 요청 + 로그인 데이터
```

- 서버가 로그인 정보를 확인한다.
- 로그인 처리 방식에 맞춰 응답한다.

⑥ 쿠키로 로그인 상태 연결
세션 쿠키를 사용하는 서비스라면:

```
서버 → 브라우저
로그인 성공 + Set-Cookie

브라우저
쿠키 저장

브라우저 → 서버
다음 요청에 Cookie 포함

서버
세션 정보를 확인해 사용자를 구별
```

- HTTP 자체가 이전 요청을 기억하는 것은 아니다.
- 쿠키와 서버의 세션 관리로 요청들을 연결한다.
  ⑦ 게시글 저장 요청

```
  POST /posts HTTP/1.1
  Host: example.com
  Content-Type: application/json
  Cookie: sessionId=abc123

{"subject":"HTTP 공부"}
```

```
브라우저 → 서버
“이 사용자가 보낸 게시글을 저장해 주세요.
내용은 JSON 형식입니다.”
```

- 다른 출처에 보내는 요청이라면 조건에 따라 CORS 사전 요청이 먼저 발생할 수 있다.

⑧ 서버 처리와 결과 응답

```
  서버
  쿠키로 사용자 확인
  → 작성 권한 확인
  → 입력 데이터 확인
  → 게시글 저장
  HTTP/1.1 201 Created
  Content-Type: application/json

{"id":1,"subject":"HTTP 공부"}

```

```
서버 → 브라우저
“새 게시글을 만들었습니다. 생성한 데이터입니다.”
```

⑨ 브라우저가 결과 반영

- JavaScript로 데이터를 요청했다면 응답을 읽어 화면을 갱신할 수 있다.
- 페이지 이동 방식으로 처리했다면 새 페이지를 불러올 수 있다.
- fetch()의 응답을 받았다는 사실만으로 화면이 자동으로 바뀌지는 않는다. 화면을 바꾸는 코드도 필요하다.

```
  사용자 행동
  ↓
  브라우저가 Request 생성
  URL + Method + Header + 필요한 Body
  ↓
  서버가 요청 확인·처리
  ↓
  서버가 Response 생성
  Status Code + Header + 필요한 Body
  ↓
  브라우저가 응답 해석
  ↓
  화면 표시·일부 갱신·페이지 이동·쿠키 저장 등
```
