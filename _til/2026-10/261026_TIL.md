I/O Bound

- data input/output
- 계산 < 대기 시간
- 데이터베이스 조회, 네트워크 통신, 외부 API 요청, 파일 읽기 및 쓰기, 사용자 입력 대기 등
- async/await 사용한 비동기 처리에 적합함

```
계산: ██
대기: ███████████████
```

CPU Bound

- 기다리는 시간 < CPU 계산 시간
- 대용량 이미지 처리, 동영상 인코딩, 복잡한 수학 계산, 데이터 압축, 머신러닝 모델 실행 등
- CPU가 계속 계산하고 있어서 async/await 사용해도 빨라지지 않음

```
계산: ███████████████
대기: ██
```

WSGI

- Web Server Gateway Interface
- python web server - python web application 통신하는 **동기** 방식의 표준 규칙
- 동기 방식->오래 걸리는 I/O 작업을 기다리는 동안 실행 작업이 대기할 수 있음
- Flask, 옛 Django 어플리케이션에서 주로 사용
- 일반적 HTTP request, response에 적합

```
WSGI
클라이언트 요청
→ 웹 서버
→ WSGI
→ Python 웹 애플리케이션
→ 응답
```

ASGI

- Asynchronous Server Gateway Interface
- python web server - python web application 통신하는 **비동기** 방식의 표준 규칙
- async, await 이용한 비동기 처리 지원
- I/O 기다리는 동안 다른 요청 처리 가능
- 많은 요청 효율적 처리
- WebSocket처럼 연결을 오래 유지하는 통신 지원
- FastAPI와 최신 Django에서 사용 가능

```
ASGI
클라이언트 요청
→ Uvicorn
→ ASGI
→ FastAPI
→ 응답
```

logging

- 프로그램 실행 동안 언제, 어디서, 어떤일 발생했는지 기록하는 기능
- 서버 정상 동작 여부 및 오류 발생 원인 확인 like CCTV
- 반복적으로 발생하는 문제 분석 가능
- 시간과 중요도를 포함하여 기록함
- 로그 레벨로 분리

```
로그 레벨
DEBUG → INFO → WARNING → ERROR → CRITICAL
```

| 로그 레벨  | 의미                          | 예시                      |
| ---------- | ----------------------------- | ------------------------- |
| `DEBUG`    | 개발 중 상세 정보 확인        | 변수 값, 실행 과정        |
| `INFO`     | 정상적인 작동 기록            | 서버 시작, 요청 처리 완료 |
| `WARNING`  | 작동하지만 주의가 필요한 상태 | 응답 지연, 만료 임박      |
| `ERROR`    | 특정 기능이 실패한 상태       | DB 조회 실패              |
| `CRITICAL` | 시스템 전체의 심각한 장애     | DB 연결 완전 중단         |

- INFO로 설정하면 INFO이상의 로그만 출력 - DEBUG 출력 x

```python
# logging 예시
import logging

logging.basicConfig(level=logging.INFO)

logger = logging.getLogger("app")

logger.info("서버가 시작되었습니다.")
logger.error("데이터베이스 연결에 실패했습니다.")
```

```python
INFO:app:서버가 시작되었습니다.
ERROR:app:데이터베이스 연결에 실패했습니다.
```

```python
# logging 기본 설정 예시
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] (%(name)s) - %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)
```

- level: 출력할 최소 로그 레벨
- format: 로그 출력 형식
- datefmt: 날짜와 시간 형식

Fast API

- Python backend web Framework
- Backend API서버를 만들 때 사용한다.
- 클라이언트의 HTTP request와 python function을 연결한다.
- python 데이터를 JSON으로 변환하여 클라이언트에 HTTP response를 보낸다.
- 즉, 클라이언트의 HTTP요청을 python 함수로 처리하고, 실행 결과를 JSON 형태의 HTTP response로 돌려줌.

특징:

- request 데이터의 타입과 필수 값을 자동 검증한다.
- `async`와 `await`을 이용한 비동기 처리를 지원한다.
- python type hint를 적극적으로 활용한다.

```
context

클라이언트: HTTP request
        ↓
Uvicorn이 요청을 받음
        ↓
FastAPI가 알맞은 Python 함수 실행
        ↓
함수가 반환한 결과를 JSON으로 변환
        ↓
클라이언트에 HTTP response 보냄
```

```python
from fastapi import FastAPI

# FastAPI 어플리케이션 생성
app = FastAPI()

@app.get("/books") # = GET /books
def get_books(): # 실제 request 처리하는 함수
    return {"books": ["어린 왕자", "1984"]} # FastAPI가 반환값을 JSON으로 변환하여 응답

```

개발에서 비즈니스 모델·도메인 모델·아키텍처 설계가 중요한 이유

- 개발은 단순히 코드를 짜는 게 아니라, 비즈니스 문제와 업무 규칙을 코드로 해결하는 과정이다.
- 설계 순서:

```
비즈니스 모델 및 문제 정의
→ 비즈니스 요구사항 분석
→ 도메인 모델 설계
→ 아키텍처 설계
→ 코드 구현
```

1. 비즈니스 모델

```
누구의 문제를 해결하는가?
어떤 가치를 제공하는가?
어떻게 서비스를 운영하는가?
어떻게 수익을 만드는가?
```

- 서비스가 위 질문에 답하는 것이 비즈니스 모델.
- 무엇을 만들기 전, "왜" 만드는지 아는 단계.

2. 비즈니스 요구사항

- 시스템이 실제로 지켜야 할 조건

```
서비스가 "도서 대여 서비스"라고 가정:
도서는 AVAILABLE 또는 RENTED 상태를 가진다.
대출 중인 도서는 다시 대출할 수 없다.
대출 중인 도서만 반납할 수 있다.
회원은 대출 가능한 도서를 조회할 수 있다.
```

3. 도메인 모델 설계

- 현실의 업무 개념, 데이터, 행동, 규칙을 코드로 표현한 것
- 도메인 모델이 없으면 비즈니스 규칙이 여러 파일에 흩어질 수 있음
- -> 도메인 모델에 규칙을 모아 < 업무 규칙 찾기, 중복 코드 줄이기, 잘못된 객체 생성 방지, 코드를 실제 업무 용어에 한정하기 > 가 용이하도록 한다.

```
"도서 대여 서비스" 도메인 예시
Book
Member
Rental
Return
Reservation
```

```
데이터
├── id
├── title
├── author
└── status

행동
├── rent()
└── return_book()

비즈니스 규칙
├── AVAILABLE 상태만 대출 가능
└── RENTED 상태만 반납 가능
```

```python
class Book:
    def __init__(self, book_id, title, author, status):
        self.id = book_id
        self.title = title
        self.author = author
        self.status = status

    def rent(self):
        if self.status != "AVAILABLE":
            raise ValueError("대출 가능한 도서가 아닙니다.")

        self.status = "RENTED"

    def return_book(self):
        if self.status != "RENTED":
            raise ValueError("대출 중인 도서가 아닙니다.")

        self.status = "AVAILABLE"
```

4. 아키텍쳐 설계

- 코드의 역할을 어떻게 나누고 연결할지 정하는 구조
- API, Application/Service, Domain, Infrastructure 4개 계층으로 나뉨.
  - API: HTTP 요청과 응답 처리
  - Application/Service: 하나의 사용 흐름을 조정
  - Domain: 핵심 비즈니스 규칙 처리
  - Infrastructure: DB, 외부 API, 파일 저장 처리 "애플리케이션이 외부 시스템과 연결되는 기술적인 부분을 담당"

```
애플리케이션
    ↓
Infrastructure
    ├── PostgreSQL
    ├── 외부 결제 API
    ├── 파일 저장소
    └── 이메일 서비스
```

전체 관계

```
비즈니스 모델
“회원이 편리하게 책을 빌릴 수 있게 한다.”
        ↓
비즈니스 요구사항
“대출 중인 책은 다시 빌릴 수 없다.”
        ↓
도메인 모델
Book.rent()에서 상태 검사
        ↓
아키텍처
API → Service → Domain → Repository
        ↓
코드 구현
POST /books/{book_id}/rent
```

멱등성

- 같은 요청을 여러번 실행해도 서버의 최종 상태가 처음 실행했을 때랑 똑같아야 함.
- 멱등성 o: 문 닫아라 -> 닫힘 -> 또 닫아라 -> 닫힘 (안변함)
- 멱등성 x: 100원 입금 -> 100원 -> 100원 입금 -> 200원
- HTTP method POST는 멱등성 x (포스트하면 값이 변하니까)
- 결제요청 같은 경우 멱등하지 않으면 중복 결제가 발생할 수 있음.
