## 1. 매크로·include·extends는 무엇을 재사용할까?

| 기능 | 재사용 대상 | 사용 예 |
| --- | --- | --- |
| `macro` | 인수를 받아 HTML을 만드는 함수 같은 조각 | 문구와 종류가 다른 버튼 |
| `include` | 현재 위치에 넣을 HTML 조각 | 헤더, 푸터, 메뉴 |
| `extends` + `block` | 페이지 전체의 공통 뼈대 | 공통 레이아웃에 페이지별 본문 넣기 |

실제 `common_macro.html`의 버튼 매크로는 다음과 같다.

```jinja2
{% macro render_button(type, text) %}
<button type="{{ type | default('button', true) }}">{{ text }}</button>
{% endmacro %}
```

```jinja2
{% from 'common_macro.html' import render_button %}
{{ render_button('submit', '저장하기') }}
```

여기서 `type`은 HTML 버튼의 동작을 정하는 값이다. `submit`, `button`, `reset` 등을 사용한다. 필기에 등장하는 `btn_type="success"`처럼 CSS 클래스를 정하는 방식과는 역할이 다르다.

`practice3.html`에서는 전체 HTML을 반복하지 않고 `base.html`을 상속한다.

```jinja2
{% extends 'layouts/base.html' %}
{% block content %}
<form method="post" action="/practice3/process">
  제목: <input type="text" name="title" />
  내용: <textarea name="content"></textarea>
  <button type="submit">작성하기</button>
</form>
{% endblock %}
```

부모 템플릿은 공통 구조와 빈자리를 정한다.

```jinja2
<body>
  {% include 'outlines/header.html' %}
  <main>{% block content %}{% endblock %}</main>
  {% include 'outlines/footer.html' %}
</body>
```

결과는 `헤더 → practice3의 폼 → 푸터`가 된다. `include`는 조각을 삽입하고, `extends`는 부모의 `block`을 채워 페이지를 완성한다.

### 질문으로 확인한 오류: include만 고치면 화면이 나올까?

처음에는 `{% include 'practice1.html %}`에서 닫는 따옴표가 빠졌다. 하지만 이를 고치는 것만으로 충분하지 않았다. 오늘 커밋의 `/practice2` 함수는 `student_context`만 만들고 **`TemplateResponse`를 반환하지 않는다.** 템플릿이 있어도 서버 함수가 렌더링 결과를 반환해야 화면으로 전달된다.

복습용으로 완성하면 다음 흐름이다.

```python
return templates.TemplateResponse(
    request=request,
    name="practice2.html",
    context=student_context,
)
```

`practice1.html`은 자체 HTML 문서 구조를 가진 연습 파일이므로, 실제 공통 조각으로 재사용할 때는 필요한 본문만 분리하는 편이 좋다.

## 2. Request와 Response는 모두 객체다

```text
브라우저 GET /practice3
    ↓
Request 객체: 메서드·주소·헤더 등 요청 정보
    ↓
FastAPI 함수 → TemplateResponse 생성
    ↓
Response 객체: 상태 코드·헤더·완성된 HTML
    ↓
브라우저가 화면 표시
```

`request: Request`는 현재 요청 객체를 주입받는 선언이다. `TemplateResponse(request=request, ...)`의 왼쪽은 인수 이름이고 오른쪽은 함수가 받은 객체다. 템플릿의 URL 생성 등에서 현재 요청 정보를 사용한다.

모든 응답에 `request` 매개변수가 필수인 것은 아니다. 단순히 딕셔너리를 반환하면 FastAPI가 일반적인 경우 이를 JSON 응답으로 변환한다.

## 3. mount는 URL과 정적 파일 폴더를 연결한다

```python
CURRENT_DIR = os.path.dirname(__file__)
app.mount(
    "/static",
    StaticFiles(directory=os.path.join(CURRENT_DIR, "static")),
    name="static",
)
```

```text
GET /static/img/cat.jpg
    ↓
/static에 연결된 StaticFiles가 처리
    ↓
chapter03-2/src/static/img/cat.jpg 반환
```

- `"/static"`: 브라우저에서 접근하는 URL 접두사
- `directory`: 실제 파일이 있는 디스크 경로
- `name="static"`: 템플릿에서 URL을 만들 때 찾는 이름

{% raw %}

```jinja2
<link rel="stylesheet"
      href="{{ url_for('static', path='/css/style.css') }}" />
```

{% endraw %}

`mount()`는 특정 경로 아래의 처리를 다른 ASGI 앱에 맡긴다. 오늘은 그 앱이 `StaticFiles`다. 각 API 함수를 모아 등록하는 `include_router()`와 구분하면 이해하기 쉽다.

## 4. 폼 입력은 어떤 형식으로 서버에 도착할까?

오늘 `practice3.html`의 폼은 파일 없이 제목과 내용만 전송한다.

```text
input name="title"에 제목 입력
textarea name="content"에 내용 입력
    ↓ POST /practice3/process
Content-Type: application/x-www-form-urlencoded
본문 예시: title=hello&content=world
    ↓
FastAPI의 Form()이 값을 읽음
```

```python
@app.post("/practice3/process")
async def jinja_practice3_process(
    title: str = Form(description="제목"),
    content: str | None = Form(default=None, description="내용"),
):
    logger.info(f"title={title}, content={content}")
```

`title`은 필수이고 `content`는 생략 가능하다. `str | None`은 허용할 타입을 말하고, `default=None`은 생략했을 때 사용할 값을 정한다. `description`은 설명이지 기본 입력값이 아니다.

현재 함수는 로그만 남기고 값을 반환하지 않으므로 정상 처리 시 응답 본문은 JSON `null`이다. 게시글을 저장하거나 완료 화면으로 이동하는 기능까지 구현한 것은 아니다.

### 개발자 도구에서 본 세 가지

| 항목 | 뜻 | 예 |
| --- | --- | --- |
| `Content-Type` | 본문을 해석하는 형식 | `application/x-www-form-urlencoded` |
| `Content-Length` | 전송하는 본문의 바이트 길이 | `22`는 22글자가 아니라 22바이트 |
| Payload | 실제로 전달하는 본문 데이터 | 제목·내용 또는 파일 데이터 |

한글은 인코딩에 따라 여러 바이트가 되고, URL 인코딩도 길이에 영향을 준다. 화면에서 보이는 글자 수와 `Content-Length`를 같다고 생각하면 안 된다.

## 5. multipart는 입력 종류가 아니라 전송 형식이다

질문하면서 구분한 핵심은 **`input type`은 무엇을 입력할지, `enctype`은 어떻게 전송할지 정한다**는 점이다.

```html
<form method="post" action="/file" enctype="multipart/form-data">
  <input type="text" name="title" />
  <input type="file" name="file" />
  <button type="submit">전송</button>
</form>
```

```text
Part 1: name="title" → 고양이 사진
boundary로 구분
Part 2: name="file", filename="cat.png"
        Content-Type: image/png → 파일의 실제 바이트
```

`multipart/form-data`는 텍스트와 파일을 각각의 파트로 나누고 boundary로 경계를 구분한다. 모든 폼이 multipart여야 하는 것은 아니다. 문자만 보내는 오늘의 작성 폼은 기본 전송 형식을 사용할 수 있다.

`uv add python-multipart`로 설치하는 라이브러리는 FastAPI의 폼·파일 데이터 해석에 사용된다. 파일 업로드뿐 아니라 `Form()`으로 일반 폼을 받을 때도 필요하다.

필기에 있는 서버 수신 예제는 다음과 같다.

```python
@app.post("/file")
async def upload_file(
    title: str = Form(...),
    file: UploadFile = File(...),
):
    return {"title": title, "filename": file.filename}
```

이 예제에는 `Form`, `File`, `UploadFile` 임포트가 필요하다. **오늘 커밋에는 업로드용 `file_test.html`은 있지만 `/file` 처리 함수와 이 템플릿을 보여 주는 경로는 아직 없다.** 전송 방식의 학습과 업로드 기능 완성은 구분해서 기록한다.

## 6. APIRouter는 도메인별 API 출입구다

```text
main.py
├── order/presentation/router.py → 주문 API
└── board/presentation/router.py → 게시판 API
```

```python
router = APIRouter(prefix="/v1/order", tags=["order", "태그1"])

@router.get("/{id}")
async def get_order_detail(id: int = Path(description="order number")):
    pass
```

최종 경로는 `/v1/order` + `/{id}`다. `prefix`는 선택 설정이며, 오늘은 공통 경로와 버전 표시에 사용했다. `/v1` 자체가 자동으로 버전을 관리해 주는 것은 아니고, 기존 계약을 유지하며 새 버전을 구분하기 위한 경로 규칙이다.

`tags`는 Swagger 문서에서 API를 묶는 용도다. 여러 태그를 지정하면 여러 그룹에 표시될 수 있지만 URL이나 권한을 바꾸지는 않는다.

```python
app.include_router(order_router)
app.include_router(board_router)
```

`app.include_router(order_router, board_router)`처럼 두 라우터를 한 호출에 넣지 않고 각각 등록한다.

![주문과 게시판 API를 그룹으로 나눈 Swagger 수업 화면](../261029-router-docs.png)

현재 주문·게시판 함수 대부분은 `pass` 또는 로그 출력만 있는 뼈대다. 경로가 문서에 나오는 것과 실제 목록 조회·상태 변경이 구현된 것은 별개다. 게시판 수정 API도 주석은 PUT이지만 실제 데코레이터는 `POST /v1/board/{id}/edit`다.

또한 주문 변경 함수의 `status: str = Body(...)`는 단일 문자열 본문을 받는다. 명세처럼 `{"status": "..."}` 객체를 받으려면 Pydantic 모델이나 `Body(embed=True)` 같은 별도 구성이 필요하다.

## 7. Depends: 공통 검사와 반환값 주입

오늘의 주문 라우터에는 공통 헤더 검사를 연결했다.

```python
def verify_secret_token(x_token: str | None = Header(None)):
    if x_token != "secret":
        raise HTTPException(status_code=403, detail="토큰이 잘못되었습니다.")

router = APIRouter(
    prefix="/v1/order",
    tags=["order", "태그1"],
    dependencies=[Depends(verify_secret_token)],
)
```

기본 설정에서 `Header()`는 Python 이름 `x_token`을 HTTP 헤더 `x-token`에 연결한다. HTTP 헤더 이름의 대소문자는 구분하지 않는다.

```bash
curl -i -H "X-TOKEN: secret" http://127.0.0.1:8000/v1/order
```

```text
주문 API 요청
    ↓
verify_secret_token 실행
    ├─ 헤더 없음·값 불일치 → 403, API 본문 실행 중단
    └─ 값이 secret → 다음 의존성·API 함수 실행
```

`Depends(verify_secret_token)`에는 함수를 전달한다. `verify_secret_token()`처럼 직접 호출한 결과를 넣는 것과 다르다. 고정 문자열 `secret`은 검사 흐름을 배우기 위한 실습 값이다.

반환값이 필요한 의존성은 함수 매개변수로 받는다.

```python
def test_func() -> str:
    return "test_fun"

@router.get("")
async def get_order_list(test: str = Depends(test_func)):
    logger.warning(f"Test: {test}")
```

- `dependencies=[Depends(...)]`: 공통 검사를 실행하고 반환값은 매개변수로 받지 않는다.
- `test=Depends(test_func)`: 실행 결과인 `"test_fun"`을 `test`에 넣는다.

### 헤더를 넣었는데 화면이 그대로인 이유

헤더 검사를 통과해도 목록 함수가 데이터를 반환하지 않으면 응답은 여전히 `null`이다. 토큰은 접근 가능 여부를 바꾸며, 화면이나 주문 데이터를 자동으로 만들어 주지 않는다.

또한 `curl`에 넣은 헤더는 **그 curl 요청에만** 적용된다. 브라우저 주소창으로 다시 접속한 요청에는 자동으로 붙지 않는다. 실제 API 요청의 헤더와 상태 코드를 확인해야 한다.

`/.well-known/appspecific/com.chrome.devtools.json`의 404는 개발자 도구가 시도하는 별도 요청이다. 주문 API의 403과 요청 경로가 다르므로 구분해서 읽는다.

## 8. CORS·X-TOKEN·TrustedHost는 서로 다른 검사다

| 구분 | 확인하는 것 | 오늘 코드·필기와의 연결 |
| --- | --- | --- |
| CORS | 다른 origin의 페이지가 브라우저에서 응답을 읽도록 허용할지 | 개념 학습, `CORSMiddleware`는 현재 코드에 없음 |
| X-TOKEN 검사 | 이 요청의 헤더 값이 서버 검사 조건을 만족하는지 | 주문 라우터의 `Depends`로 연결 |
| TrustedHost | 요청 `Host` 헤더가 허용된 호스트인지 | `localhost`, `127.0.0.1` 허용 |

Origin은 **프로토콜·호스트·포트**의 조합이다. 같은 컴퓨터에서도 `http://localhost:3000`과 `http://localhost:8000`은 포트가 달라 다른 출처다.

CORS는 브라우저가 적용하는 규칙이다. 일부 요청은 사전 요청(preflight)으로 제한하고, 단순 요청은 서버에 도착해도 브라우저가 응답을 읽지 못하게 할 수 있다. 따라서 CORS를 모든 외부 요청을 차단하는 인증 기능으로 보면 안 된다. curl이나 서버 간 통신에는 브라우저의 CORS 제한이 적용되지 않는다.

```python
app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=["localhost", "127.0.0.1"],
)
```

이 설정은 **클라이언트 IP 허용 목록이 아니라 요청 Host 검사**다. 서버를 로컬에서만 듣게 만드는 설정이나 사용자 인증을 대신하지 않는다.

## 9. 미들웨어는 요청과 응답을 감싼다

```python
@app.middleware("http")
async def middleware1(request: Request, call_next):
    logger.info("middleware1()의 요청 처리 전")
    response = await call_next(request)
    logger.info("middleware1()의 응답 처리 전")
    return response
```

`call_next`는 조건을 나누는 분기문이 아니라, **요청을 다음 처리 단계에 넘기고 응답을 받아오는 함수**다. 앞부분에서는 요청을 검사하거나 시간을 기록하고, 뒷부분에서는 돌아온 응답을 확인·수정할 수 있다.

![클라이언트 요청과 응답 사이에서 실행되는 미들웨어 수업 도식](../261029-middleware.png)

오늘처럼 `middleware1` 다음에 `middleware2`를 등록하면 두 함수 사이에서는 나중에 등록한 것이 바깥을 감싼다.

```text
요청 → middleware2 전처리
       → middleware1 전처리
         → 의존성 검사·API 함수
       ← middleware1 후처리
     ← middleware2 후처리 → 응답
```

그래서 로그는 `2 요청 전 → 1 요청 전 → 1 응답 전 → 2 응답 전` 순서다. 실제 앱에는 그 뒤 추가한 `TrustedHostMiddleware`도 더 바깥에 있으므로, 허용되지 않은 Host는 안쪽 API에 도달하기 전에 거절될 수 있다.

## 10. SSR·CSR와 SEO를 연결해서 이해하기

| 구분 | 서버 렌더링 SSR | 클라이언트 렌더링 CSR |
| --- | --- | --- |
| 화면을 만드는 곳 | 서버 | 브라우저의 JavaScript |
| 첫 HTML | 주요 내용이 포함됨 | 최소 뼈대일 수 있음 |
| 오늘의 연결 | FastAPI + Jinja2 | 일반적인 React CSR 구성과 비교 |
| 고려할 점 | 서버 처리·DB 조회가 느리면 응답 지연 | JS 다운로드·실행·데이터 요청 뒤 내용 표시 |

```text
Jinja2 SSR: 요청 → 서버에서 데이터와 템플릿 결합 → 완성된 HTML 전달
React CSR: HTML·JS 수신 → 브라우저에서 JS 실행 → 데이터 조회·화면 생성
```

SEO는 검색 엔진이 페이지 내용을 이해하고 검색 결과에 잘 노출하도록 돕는 작업이다. 주요 내용이 첫 HTML에 있으면 검색 엔진이 JavaScript 실행을 기다리지 않고 읽을 수 있어 유리하다. 다만 SSR이 항상 더 빠르거나 검색 순위를 보장하는 것은 아니다.

**React가 항상 CSR인 것도 아니다.** Next.js 같은 구성에서는 React도 SSR·SSG를 사용할 수 있다. 라이브러리 이름보다 실제로 HTML을 어디서, 언제 만드는지 구분해야 한다.

## 11. 작지만 함께 배운 명령어

`mkdir`은 폴더를 만든다. Markdown 파일을 만들려면 다음처럼 사용할 수 있다.

```bash
touch note.md
```

파일이 이미 있으면 내용을 비우지 않고 수정 시간을 갱신한다.

## 오늘의 핵심 정리

1. Jinja2의 매크로는 함수 같은 조각, include는 HTML 조각 삽입, extends는 전체 레이아웃 상속이다.
2. 템플릿 파일을 작성하는 것과 처리 함수가 HTML 응답을 반환하는 것은 별도 단계다.
3. `mount`는 URL 아래의 처리를 정적 파일 앱 등에 맡기고, `include_router`는 기능별 API를 등록한다.
4. 입력 종류와 전송 형식은 다르다. `type`, `name`, `enctype`, `Form`·`File`의 연결을 따라가야 한다.
5. `Depends`는 공통 검사를 실행하거나 필요한 값을 API 함수에 주입한다.
6. CORS, 토큰 검사, Host 검사는 목적이 다르므로 오류를 같은 원인으로 묶지 않는다.
7. 미들웨어는 바깥에서 요청을 받고 응답 때 역순으로 돌아온다.
8. SSR/CSR는 화면을 조립하는 위치의 차이이며, 성능·SEO는 실제 구성에 따라 판단한다.

## 회고

오늘 기록을 돌아보면 ‘라우터는 왜 나누는가’, ‘Request와 Response는 둘 다 객체인가’, ‘헤더를 넣으면 무엇이 달라져야 하는가’처럼 코드의 역할과 연결을 묻는 질문이 많았다. 한 줄의 문법을 아는 것과 그 줄이 요청 흐름의 어디에 있는지 이해하는 것은 다르다는 점을 복습했다.

특히 화면이 안 나오는 문제를 템플릿 문법만으로 설명할 수 없고, 헤더 검사를 통과했다고 실제 주문 데이터가 만들어지는 것도 아니라는 점이 기억할 부분이다. 앞으로는 브라우저가 보낸 주소·헤더·본문을 먼저 보고, 어떤 미들웨어와 의존성을 거쳐 함수가 실행되는지, 마지막으로 무엇을 반환하는지 순서대로 확인하고 싶다. 다음 실습에서는 아직 뼈대인 API와 파일 업로드를 직접 완성하며 이 흐름을 다시 점검해야겠다.
