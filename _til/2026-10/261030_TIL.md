## 1. 파일 업로드는 작은 조각으로 읽고 쓴다

`UploadFile`은 업로드된 파일을 나타낸다. 파일 전체를 한 번에 메모리로 읽는 대신, 아래 코드는 최대 5 MiB씩 읽어서 디스크에 기록한다.

```python
async with aiofiles.open(physical_target_path, "wb") as disk_file:
    while True:
        chunk = await file.read(1024 * 1024 * 5)
        if not chunk:
            break
        await disk_file.write(chunk)
```

`aiofiles`는 파일 I/O를 `async`/`await` 흐름에서 다룰 수 있게 한다. `await` 중에는 이벤트 루프가 다른 작업을 진행할 수 있다. 비동기 방식이 디스크 자체를 더 빠르게 만드는 것은 아니지만, 파일 작업이 진행되는 동안 서버가 다른 요청을 처리할 여지를 준다.

청크 단위 처리는 메모리 사용량도 일정하게 유지하는 데 도움이 된다. 예를 들어 12 MiB 파일은 한 번에 12 MiB 전체를 읽는 대신, 대략 `5 MiB + 5 MiB + 2 MiB`로 나뉘어 처리된다.

파일을 저장하기 전에 `os.path.basename()`으로 파일명에서 경로 부분을 제거하고, `seq_{id}_`를 붙여 디스크 경로를 만든다. 저장 중 실패하면 이미 만들어진 파일을 삭제해 불완전한 파일이 남지 않게 한다.

## 2. 파일 다운로드는 응답에 나눠서 흘려보낸다

다운로드 함수는 `get_file_chunk()`라는 비동기 제너레이터를 `StreamingResponse`에 넘긴다.

```python
async def get_file_chunk(file_path, chunk_size=1024 * 1024):
    async with aiofiles.open(file_path, "rb") as file:
        while True:
            chunk = await file.read(chunk_size)
            if not chunk:
                break
            yield chunk

return StreamingResponse(
    get_file_chunk(physical_target_path),
    media_type=asset.content_type,
    headers={
        "Content-Disposition": f'attachment; filename="{asset.filename}"',
        "Content-Length": str(asset.file_size),
        "Cache-Control": "no-cache",
    },
)
```

`yield`는 파일 전체가 준비될 때까지 기다리지 않고 읽은 조각을 하나씩 응답으로 보낸다. 그래서 큰 파일을 응답용 메모리에 전부 올리는 일을 피할 수 있다. `Content-Disposition`은 브라우저에 첨부 파일로 내려받도록 알리고, `Content-Length`와 `Content-Type`은 크기와 파일 형식을 알려준다.

요청 흐름은 다음과 같다.

```text
GET /assets/1/download
    ↓
메모리 저장소에서 자산 정보 확인
    ↓
실제 파일 경로와 존재 여부 확인
    ↓
파일을 1 MiB씩 읽는 비동기 제너레이터
    ↓
StreamingResponse가 조각을 응답으로 전송
```

이 실습의 `asset_repository`는 DB가 아니라 파이썬 딕셔너리다. 서버를 재시작하면 자산 목록과 ID가 초기화되므로, 파일 관리 기능을 실제 서비스에 적용하려면 메타데이터를 영구 저장소에 보관해야 한다.

## 3. 도메인 객체가 자신의 규칙을 검사한다

`MultimediaAsset`은 파일명과 크기를 검사하고, 자산 상태를 관리한다.

```text
PENDING → PROCESSING → COMPLETED
```

`mark_as_processing()`은 `PENDING`일 때만, `mark_as_completed()`는 `PROCESSING`일 때만 상태를 바꾼다. 잘못된 순서로 호출하면 `ValueError`를 발생시킨다. 객체가 자기 데이터와 상태 변경 규칙을 함께 가지는 방식이다.

다만 현재 업로드 API는 새 자산을 기본 상태 `PENDING`으로 만들고 저장한다. 코드에서 위 두 상태 변경 메서드를 호출하지 않으므로, 업로드만으로 `COMPLETED`까지 전이하는 것은 아니다. 응답 스키마의 설명과 실제로 실행되는 흐름은 구분해서 읽어야 한다.

## 4. 응답을 먼저 보내고 후속 작업을 실행한다

`BackgroundTasks`에는 응답을 반환하기 전에 등록할 작업을 추가할 수 있다.

```python
async def send_email(email: str):
    await asyncio.sleep(3)  # 메일 전송을 흉내 내는 대기
    logger.info("회원가입 안내 메일 전송 완료...")

@app.get("/signup")
async def signup_done(background_tasks: BackgroundTasks):
    background_tasks.add_task(send_email, "test@test.org")
    return {"message": "회원가입이 완료 되었습니다."}
```

브라우저에는 완료 응답이 먼저 도착하고, 약 3초 뒤 서버 로그에 메일 작업 완료 메시지가 기록된다. 여기서는 `asyncio.sleep()`으로 작업 시간을 흉내 냈으며 실제 이메일을 보내지는 않는다.

FastAPI의 `BackgroundTasks`는 응답 뒤 실행할 간단한 작업에 편리하다. 프로세스가 종료되어도 작업을 보존해야 하거나, 오래 걸리고 실패 재시도가 필요한 작업이라면 별도의 작업 큐를 고려해야 한다.

## 5. ORM과 커넥션 풀은 서로 다른 역할이다

오늘 필기에서 가장 헷갈리지 않게 정리할 부분은 ORM과 커넥션 풀의 역할이다.

| 개념 | 하는 일 |
| --- | --- |
| ORM | 파이썬 객체와 관계형 DB의 테이블·행을 연결해 다루도록 돕는다 |
| Engine / 커넥션 풀 | DB 연결을 만들고, 사용 가능한 연결을 관리·재사용한다 |
| Session | 작업 중인 객체와 트랜잭션을 관리하고, 변경 사항을 DB에 반영한다 |

```text
파이썬 객체 → ORM이 SQL로 변환 → 커넥션을 통해 DB에 질의
```

커넥션 풀은 요청마다 DB 연결을 새로 만드는 비용을 줄이고, 동시에 열어 둘 연결 수를 관리한다. 풀의 연결을 빌려 쿼리를 실행한 뒤에는 연결을 닫아 없애기보다 풀에 돌려준다. `pool_size`를 무작정 크게 잡으면 애플리케이션 인스턴스 수까지 곱해져 DB 연결 한도를 넘을 수 있으므로, DB가 감당할 전체 연결 수를 고려해야 한다.

세션에서는 객체를 `add()`하는 것과 DB에 `commit()`하는 것을 구분한다. `add()`는 변경 대상을 세션에 등록하는 단계이고, `commit()`은 트랜잭션을 확정해 DB에 반영하는 단계다. 중간에 문제가 생기면 `rollback()`으로 해당 트랜잭션의 변경을 취소할 수 있다.

오늘 커밋의 `chapter05-1`에는 SQLAlchemy 관련 의존성과 `.env.local`을 읽는 설정 파일, 로거 설정이 있다. 하지만 이 커밋에서 Engine이나 Session을 생성해 실제 쿼리를 실행하는 코드는 아직 확인되지 않는다. 따라서 ORM과 풀은 필기에서 정리한 개념으로 기록하고, DB 연결 실습을 완료했다고 쓰지 않았다. 또한 `POOL_SIZE`는 `os.getenv()` 결과라 문자열이므로 실제 엔진 설정에 전달할 때는 정수 변환이 필요하다.
