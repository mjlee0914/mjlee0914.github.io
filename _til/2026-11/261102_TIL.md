## 1. PostgreSQL, Docker, DBeaver는 서로 다른 역할이다

처음에는 PostgreSQL과 DBeaver가 API 흐름 안에서 순서대로 실행되는 것처럼 느껴졌는데, 실제로는 역할이 다르다.

```text
FastAPI / SQLAlchemy ───────▶ PostgreSQL 서버
                                  ▲
                                  │ 별도 연결
                              DBeaver
```

- **PostgreSQL**은 데이터를 실제로 저장하고 SQL을 실행하는 데이터베이스 서버다.
- **Docker**는 수업용 PostgreSQL 서버를 컨테이너로 실행하는 방법이다.
- **DBeaver**는 같은 PostgreSQL에 별도로 접속해 테이블과 데이터를 확인하는 DB 클라이언트다.

API가 DBeaver를 거쳐 DB에 도달하는 것은 아니다. FastAPI와 DBeaver가 각각 같은 서버에 접속한다. 그래서 DBeaver에서 테이블이 보이는지는 DB 상태를 확인하는 방법이고, FastAPI 요청이 어떤 계층을 통과했는지를 보여주는 것은 아니다.

## 2. 모델 클래스와 실제 DB 테이블 사이에는 등록 단계가 있다

`models.py`에 `class Post(Base)`를 작성하는 것은 테이블 설계 정보를 파이썬에 선언하는 단계다. 그 파일이 import되어 `Base.metadata`에 등록되고, 그 다음 DB에 테이블을 만들라는 작업이 실행되어야 실제 테이블이 생긴다.

오늘 수업 예제의 시작 순서는 다음과 같다.

```text
FastAPI lifespan 시작
    ↓
init_models()가 User·Board 모델 모듈 import
    ↓
모델 클래스가 Base.metadata에 등록
    ↓
engine.begin() 안에서 Base.metadata.create_all 실행
    ↓
PostgreSQL에 없는 테이블 생성
```

따라서 **모델 코드가 있다는 것**과 **DB에 테이블이 만들어졌다는 것**은 같은 말이 아니다. 모델이 import되지 않았거나, `create_all` 또는 마이그레이션 실행 단계가 없으면 DB에는 변화가 없을 수 있다.

이 차이는 Team D에도 바로 연결된다. 현재 Team D에는 `Base`와 DB 세션 설정이 있고 Festival·Performance SQLAlchemy 모델도 추가됐다. 하지만 현재 작업 트리의 `src/shared/core/models.py`에서는 모델 import가 주석 처리되어 있고, `src/main.py`에서도 모델 초기화와 `create_all` 호출을 확인하지 못했다. 그러므로 **현재 코드만 근거로 실제 PostgreSQL 테이블이 생성되었다고 말할 수는 없다.** 테이블 생성은 모델 선언과 별도로 연결해야 하는 작업이다.

## 3. `commit()`은 DB 저장이고 `return`은 HTTP 응답이다

게시판 예제에서 `test1()`은 Board와 Post 객체를 세션에 추가하고 `await session.commit()`을 호출하지만 응답용 `return`은 작성하지 않는다.

```python
session.add(board)
session.add(post)
await session.commit()  # DB 트랜잭션 확정
# return이 없으면 Python 함수 결과는 None
```

여기서 DB에 저장하는 동작은 `commit()`이 수행한다. `return`은 브라우저나 API 클라이언트에 무엇을 응답할지 정한다. 따라서 테스트 API가 저장만 확인하는 목적이라면 응답 데이터를 돌려주지 않을 수 있고, FastAPI는 기본적으로 `None` 결과를 응답 본문 `null`로 처리한다.

```text
session.add() → 세션이 변경 대상을 추적
session.commit() → 트랜잭션을 DB에 반영
session.refresh() → DB가 채운 값 등을 객체에 다시 읽음
return → 클라이언트에 보낼 응답 결정
```

이 네 단계를 구분하면 “화면에 응답이 없거나 `null`인데 DB에는 왜 저장됐지?”라는 질문도 풀린다. 저장과 응답은 서로 다른 책임이다.

## 4. 네 계층은 요청을 역할별로 나눈다

ax_study 예제는 사용자 등록 흐름에서 각 계층이 맡는 일을 보여준다.

| 계층 | 맡는 일 | 오늘 본 코드의 예 |
| --- | --- | --- |
| Presentation | HTTP 요청·응답, FastAPI 의존성 연결 | `user/presentation/routers/v1/router.py` |
| Application | 사용 사례의 순서 조정 | `UserService.register_user()` |
| Domain | 업무 규칙과 저장소 인터페이스 | `User.create()`, `UserRepository` |
| Infrastructure | SQLAlchemy 모델과 실제 DB 처리 | `UserModel`, `SqlAlchemyUserRepository` |

회원가입 요청은 아래처럼 흐른다.

```text
POST /v1/users
    ↓
Presentation Router가 요청 Schema를 받음
    ↓ Depends
Application Service가 회원가입 절차를 조정
    ↓
Domain이 이메일·이름·비밀번호 규칙을 확인
    ↓
Infrastructure Repository가 SQLAlchemy로 저장
    ↓
PostgreSQL에 INSERT · 응답 Schema로 결과 반환
```

`Depends(get_db)`는 요청을 처리할 `AsyncSession`을 제공하고, `container.py`는 Repository와 Service를 조립해 FastAPI에 연결한다. Router가 SQL을 직접 작성하지 않고, Domain이 SQLAlchemy에 직접 의존하지 않도록 역할을 나누는 것이 핵심이다.

## 5. 게시판 1:N 관계 조회는 필요한 데이터를 미리 정한다

수업 예제에서 Board 하나에는 Post 여러 개가 연결된다.

```text
Board 1 ───────── N Post
Board.posts              Post.board_config
```

`joinedload(Post.board_config)`는 Post 여러 개에서 각각의 Board 하나를 함께 읽는 다대일 조회에 쓰였다. `selectinload(Board.posts)`는 Board를 먼저 조회한 뒤 해당 Board들의 게시글 목록을 추가 조회하는 일대다 조회에 쓰였다. 둘 다 관계 데이터를 필요할 때마다 반복 조회하는 일을 줄이기 위한 로딩 방식이다.

## 6. Team D에서 이어지는 적용

오늘 Team D의 커밋에는 Festival·Performance SQLAlchemy 모델과 데이터 제약 조건이 추가됐다. 예를 들어 공연 시작·종료 시각, 예매 기간, 수용 인원, 잔여 수량, 가격의 기본 범위를 DB 제약 조건으로 표현하고, `updated_at`은 생성 직후 값이 없을 수 있어 nullable로 조정했다.

이 모델들이 자리 잡을 계층도 나눠 볼 수 있다.

```text
Presentation: /api/v1/festivals, /api/v1/performances 라우터와 요청·응답 Schema
Application: 등록·조회·수정 같은 사용 사례 조정
Domain: 페스티벌·공연의 업무 규칙
Infrastructure: SQLAlchemy 모델, Repository, PostgreSQL 접근
```

현재 로컬 작업 트리에서는 `main.py`에 `/api/v1` 라우터 묶음을 연결하고 Festival·Performance 라우터를 작성 중이다. 다만 `schemas.py`는 아직 비어 있고, 일부 라우터의 `response_model`·요청 타입 자리가 미완성 상태라 API 구현이 끝났거나 실행 검증됐다고 기록하지 않았다. **라우터를 등록하는 것**은 URL 처리를 연결하는 일이고, **DB 모델을 등록하고 테이블을 생성하는 것**은 별도의 일이다.

## 오늘 정리한 점

오늘 가장 큰 정리는 PostgreSQL, DBeaver, Docker를 서로 다른 역할로 볼 수 있게 된 것이다. Docker는 DB 서버를 실행하고, PostgreSQL은 데이터를 저장하며, DBeaver는 그 DB에 따로 접속해 상태를 보여준다. FastAPI 요청은 SQLAlchemy를 통해 PostgreSQL에 직접 연결된다.

또 모델 클래스를 작성했다고 테이블이 바로 만들어지는 것도 아니었다. 모델 모듈이 `Base.metadata`에 등록된 다음 테이블 생성 또는 마이그레이션 단계가 있어야 한다. `commit()`은 DB에 저장하고 `return`은 HTTP 응답을 정한다는 것도 구분했다.

수업 예제에서 본 네 계층을 Team D 코드에 대입해 보니, 지금 작성 중인 Performance 라우터가 결국 Schema → Router → Service → Repository → DB 흐름으로 이어져야 한다는 점이 보였다. 다음에는 요청·응답 Schema와 Service/Repository 연결을 마무리하고, 모델 등록과 테이블 생성 경로를 확인한 뒤 실제 API 요청과 DBeaver 결과를 각각 확인해 보려고 한다.
