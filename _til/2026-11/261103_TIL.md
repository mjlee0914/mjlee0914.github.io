## 1. `back_populates`는 양쪽 객체 속성을 연결한다

Board 하나에 Post 여러 개가 속하는 1:N 관계를 예로 들면, 각 클래스의 relationship이 상대편 속성을 가리킨다.

```python
class Board(Base):
    posts: Mapped[list["Post"]] = relationship(
        back_populates="board_config",
    )


class Post(Base):
    board_config: Mapped["Board"] = relationship(
        back_populates="posts",
    )
```

`Board.posts`의 `back_populates="board_config"`은 Post 쪽 속성을 가리키고, `Post.board_config`의 `back_populates="posts"`는 Board 쪽 속성을 가리킨다. 따라서 Python 객체에서 한쪽 관계를 설정하면 SQLAlchemy가 반대쪽 관계도 일관되게 다룰 수 있다.

```text
Board.posts  ←────────→  Post.board_config
   1                         N
```

`back_populates`는 SQL `JOIN`을 대신하지 않는다. 객체 사이의 관계를 선언하며, 실제 데이터를 가져오는 SQL은 로딩 전략에 따라 SQLAlchemy가 구성한다.

## 2. `lazy`는 관계 데이터를 불러오는 전략이다

관계 속성을 접근할 때 관련 데이터를 언제 어떤 쿼리로 가져올지 정한다. 오늘 모델에서는 `Board.posts`에 `selectin`, `Post.board_config`에 `joined`를 사용했다.

### `selectin`: 부모와 자식을 나눠 조회

```python
posts = relationship(
    back_populates="board_config",
    lazy="selectin",
)
```

게시판을 먼저 조회하고, 그 게시판들의 게시글을 `IN (...)` 조건을 사용하는 추가 쿼리로 한꺼번에 가져오는 방식이다. 부모가 여러 개일 때 자식 목록을 모아 조회하므로, 부모마다 자식을 따로 조회하는 반복 쿼리를 줄여준다.

### `joined`: 처음부터 JOIN

```python
board_config = relationship(
    back_populates="posts",
    lazy="joined",
)
```

게시글과 각 게시글의 게시판처럼 N:1 관계 데이터를 처음 조회부터 JOIN으로 함께 가져온다.

### `raise`: 명시하지 않은 접근을 오류로 표시

`lazy="raise"`를 사용하면 로딩하지 않은 관계 속성에 접근할 때 오류가 나므로, 조회 코드에서 필요한 eager loading을 빠뜨렸는지 찾을 수 있다. 단, 실제 설정의 기본값은 프로젝트 구성에 따라 확인해야 하며 항상 `raise`라고 단정할 수는 없다.

로딩 방식은 상황에 맞춰 고른다. `selectin`은 1:N 목록에, `joined`는 N:1처럼 단일 관계 데이터에 자주 쓰인다. `back_populates`가 로딩 방식을 정하는 것은 아니다.

## 3. `cascade`는 ORM 작업을 관계 객체에 전파한다

Board 모델에는 다음 설정이 있다.

```python
posts = relationship(
    back_populates="board_config",
    lazy="selectin",
    cascade="all, delete-orphan",
)
```

`all`은 주요 ORM 상태 변경을 자식 객체에도 전파한다. 예를 들어 새 Board에 Post를 붙이고 Board를 세션에 추가하면, 관계를 따라 Post도 저장 대상으로 처리된다.

`delete-orphan`은 Post가 Board와의 관계에서 제거되어 부모 없는 상태가 되면 그 Post를 삭제 대상으로 표시한다. 자식이 부모 없이 존재할 수 없는 소유 관계에서 유용하다.

이 옵션은 Python 객체와 SQLAlchemy ORM의 작업을 다룬다. DB 외래 키의 `ondelete="CASCADE"`는 실제 PostgreSQL 제약 조건을 통해 행 삭제를 처리하므로 서로 다른 계층의 설정이다. DB 작업까지 의도한 대로 되는지는 외래 키와 DB 설정도 확인해야 한다.

## 4. Post와 Tag는 중간 테이블을 쓰는 N:M 관계다

게시글 하나는 태그 여러 개를 가질 수 있고, 태그 하나도 여러 게시글에 붙을 수 있다. 두 테이블을 직접 연결하는 대신 `posts_tags` 중간 테이블을 둔다.

```python
post_tag_association = Table(
    "posts_tags",
    Base.metadata,
    Column("post_id", BigInteger, ForeignKey("posts.id"), primary_key=True),
    Column("tag_id", BigInteger, ForeignKey("tags.id"), primary_key=True),
)

class Post(Base):
    tags = relationship(
        secondary=post_tag_association,
        back_populates="posts",
        lazy="selectin",
    )

class Tag(Base):
    posts = relationship(
        secondary=post_tag_association,
        back_populates="tags",
        lazy="selectin",
    )
```

`secondary`가 연결 테이블을 지정하고, `back_populates`는 Post와 Tag 양쪽에서 관계를 탐색하게 한다. 이 역시 관계를 정의하는 설정이며, 필요할 때 실제 조회 쿼리가 실행된다.

## 오늘 정리한 점

세 옵션을 기능별로 나누니 `relationship()` 설정을 읽기 쉬워졌다.

| 설정 | 하는 일 |
| --- | --- |
| `back_populates` | 양쪽 Python 객체 관계를 연결 |
| `lazy` | 관계 데이터를 가져오는 시점과 쿼리 전략 지정 |
| `cascade` | ORM 작업을 관련 객체에 전파 |
| `ondelete="CASCADE"` | DB 외래 키에서 삭제 규칙 지정 |

특히 `back_populates`와 `JOIN`은 경쟁하는 선택지가 아니고, `cascade`와 `ondelete`도 같은 설정의 중복 표현이 아니다. 다음에는 관계를 저장하고 조회하는 작은 실습에서 ORM 동작과 실제 SQL, DB 결과를 각각 확인해 보려고 한다.
