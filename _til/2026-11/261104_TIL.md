Festival 상태는 DB 컬럼에 저장하지 않고 시작일·종료일·취소 시각으로 계산한다. 상태 계산에 기준 날짜를 전달하면 날짜 경계를 확인하기 쉽고 테스트에서도 날짜를 고정할 수 있다. 취소 상태를 먼저 확인해 취소가 일정 상태보다 우선하도록 했다.

도메인 객체는 시작일이 종료일보다 앞서야 한다는 규칙을 검사한다. 기간을 변경할 때는 전달된 값과 기존 값을 합친 뒤 다시 검증한다. 취소는 서버 시각을 받아 기록하고, 이미 취소된 축제의 중복 취소는 예외로 처리한다. DB 모델에도 시작일이 종료일보다 빠르다는 체크 제약을 두었다.

현재 로컬 변경에는 FestivalRepository 인터페이스, Festival·Performance 라우터 뼈대, Performance 상태 enum 분리가 있다. 이 부분은 아직 미완성이고 커밋되지 않았다. 라우터 핸들러와 Infrastructure 저장 구현은 계속 작업해야 한다.

다음에는 요청·응답 스키마를 API 명세에 맞추고 Repository와 라우터를 연결할 예정이다. Festival 상태를 계산하는 모델 설계와 API 응답 필드를 함께 확인해야 한다.

## 1. 토큰 발급과 검증

일반적인 로그인에서는 서버가 사용자를 확인한 뒤 토큰을 발급한다. 브라우저는 토큰을 보관하고 API 요청마다 함께 보내며, 서버는 서명과 만료 여부를 확인한 뒤 사용자의 권한도 검사한다.

- 인증(Authentication): 요청한 사용자가 누구인지 확인
- 인가(Authorization): 해당 사용자가 이 작업을 할 수 있는지 확인

따라서 토큰이 유효해도 요청한 작업을 할 권한이 없으면 거부해야 한다. 인증 정보가 없거나 유효하지 않으면 보통 401, 인증은 되었지만 권한이 없으면 403을 반환한다. JWT는 서버가 서명을 직접 검증할 수 있지만, 불투명한 임의 문자열 토큰은 서버 저장소를 조회하는 방식이 흔하다.

## 2. OAuth 인가 코드와 토큰

카카오 로그인에서 사용자가 동의하면 카카오는 우리 서버에 인가 코드를 전달한다. 이 코드는 액세스 토큰이 아니라 서버가 카카오에 제출해 토큰으로 교환하는 짧은 수명의 코드다. 서버는 카카오 토큰으로 사용자 정보를 확인한 뒤 우리 서비스의 회원 처리와 로그인을 마친다.

카카오 액세스 토큰은 카카오 API 사용을 위한 토큰이고, 우리 서비스의 세션이나 JWT는 FastAPI 서비스에 로그인하기 위한 수단이다. OAuth는 외부 서비스 접근 권한 위임에 쓰이며, 사용자 인증 정보를 표준화하려면 OIDC를 함께 사용할 수 있다.

## 3. JWT와 비밀번호 저장

JWT는 Header, Payload, Signature로 구성된다. 일반적인 서명 JWT에서 헤더와 페이로드는 인코딩되어 있을 뿐 암호화되지 않으므로 누구나 내용을 읽을 수 있다. 비밀번호나 민감한 개인정보를 넣지 않고, 서버는 서명과 만료 시간, 발급자와 대상 등을 검증해야 한다.

비밀번호는 bcrypt처럼 salt를 포함하고 계산을 의도적으로 늦추는 비밀번호 해시로 저장한다. 같은 비밀번호도 salt가 다르면 해시 결과가 달라질 수 있다. 로그인 때는 원문을 복호화하는 대신 검증 함수로 입력값과 저장된 해시를 비교한다. 빠른 범용 해시만으로 비밀번호를 저장하면 대입 공격에 취약해질 수 있다.

## 4. DIP와 의존성 주입

인증 서비스가 JWT 구현체를 내부에서 직접 생성하면 특정 기술에 묶인다. TokenProvider 같은 추상화에 의존하고 조립 단계에서 구현체를 전달하면 교체할 때 도메인 로직의 수정 범위를 줄일 수 있다.

의존성 역전 원칙(DIP)은 핵심 정책이 세부 구현이 아닌 추상화에 의존하게 하는 설계 원칙이다. 의존성 주입(DI)은 필요한 객체를 외부에서 전달하는 기법이며, FastAPI에서는 Depends()로 서비스 객체를 라우터에 주입할 수 있다.

## 5. CORS와 캐시

CORS는 브라우저가 다른 출처의 리소스를 읽도록 서버가 허용하는 규칙이다. 출처는 프로토콜·호스트·포트의 조합이며, CORS 설정은 인증과 권한 검사를 대신하지 않는다.

캐시는 자주 조회하는 결과를 임시 보관해 반복 조회를 빠르게 한다. 요청 결과가 있으면 Cache Hit, 없거나 만료되면 Cache Miss다. TTL은 캐시 유지 시간이며, 데이터 수정 때 캐시를 무효화하거나 갱신하는 정책도 함께 고려해야 한다.
