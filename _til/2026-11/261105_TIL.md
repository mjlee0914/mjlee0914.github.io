# 2026-11-05 개인 작업일지

## 무엇을 어떻게 했나

- Festival 도메인 예외가 공통 예외 체계를 사용하도록 변경함. `FestivalNotFound`, `InvalidFestivalPeriod`, `FestivalAlreadyCanceled`, `FestivalPeriodOverlap`이 각각 공통 `NotFoundException`, `UnprocessableException`, `ConflictException`을 상속하도록 정리하고 고정 `error_code`를 지정함.
- Festival Entity에서 잘못된 기간과 중복 취소를 검사할 때 도메인 예외의 기본 메시지를 사용하도록 수정함.
- Performance SQLAlchemy 모델을 공통 `DateTimeMixin`을 사용하는 구조로 변경하고, `PerformanceStatus`를 `performances/domain/enums.py`의 `StrEnum`으로 분리함. 같은 Festival 안에서 회차명이 중복되지 않도록 `(festival_id, title)` 복합 UniqueConstraint를 추가함.
- Festival Domain Repository 인터페이스에 단건 조회, 페이지 목록, 전체 개수, 저장, 같은 장소의 기간 중복 확인 메서드를 정의함. 구현 커밋은 11월 4일 밤에 만들어졌으며, 11월 5일 PR #64로 병합됨.
- GitHub 저장소에서 팀 작업으로 전역 예외 핸들러와 공통 예외 사용법, 인증 패키지 구조 변경이 병합된 것을 확인함. 이 항목들은 팀 저장소 반영 사항으로 확인했으며 본인 단독 기여로 기록하지 않음.
- Performance 도메인 구현을 시작함. 공연 일정·예매 기간·축제 기간·수량·가격·취소 규칙을 Entity 문서와 코드로 정리하고, 도메인 예외 초안 및 Repository·Application Service·Router 파일 틀을 작성함. 이 파일들은 현재 로컬에서 작성 중이며 완성된 기능은 아님.

## 막힌 점·고민

- Performance 일정 검증은 축제 기간 안에 공연이 포함되는지 확인해야 하지만, Performance 도메인이 Festival 도메인에 직접 의존하지 않도록 날짜 값만 전달하는 방식을 고려해야 함.
- 부분 수정에서는 요청에 포함된 값과 기존 값을 합친 최종 일정·예매 기간을 검증해야 함.
- 전역 예외 핸들러가 도메인 예외를 공통 실패 응답으로 바꾸도록 연결됐으므로, 각 도메인 예외의 HTTP 상태 코드와 `error_code`를 일관되게 매핑할 필요가 있음.
- 현재 Performance Repository와 Application Service는 파일 초안만 있고 실제 조회·저장·트랜잭션 흐름은 구현되지 않음.

## 어떻게 풀었나

- Festival 도메인 예외를 공통 예외의 세부 유형으로 바꾸고 상태 코드 의미에 맞춰 분류함: 찾을 수 없음은 404, 규칙 위반은 422, 현재 상태와 충돌은 409.
- Festival Repository는 DB 구현 세부사항 대신 필요한 메서드 계약만 도메인 계층에 두고, 저장 작업의 `commit`은 Application Service 책임으로 정리함.
- Performance의 상태값을 Domain `StrEnum`으로 분리해 모델과 도메인이 같은 상태 정의를 사용하도록 함.
- Performance의 회차명 중복 조건을 전역 제목 중복이 아닌 Festival 내부 중복으로 제한해 복합 유니크 제약으로 표현함.
- 구현 여부가 불분명한 Performance 코드는 초안으로 표시하고, 병합된 커밋 및 PR과 현재 작업 중 파일을 기록에서 구별함.
