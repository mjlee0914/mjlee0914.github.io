# 카락페 프로젝트 작업 기록 — 2026-11-05~11

이 문서는 Team D 카락페 프로젝트에서 담당한 Festival·Performance 영역의 작업을 날짜별로 정리한 기록이다.
완료한 구현, `dev` 병합, 리뷰 중인 작업, 검증 범위를 구분해 기록했다.

## 2026-11-05 — 공통 예외 체계와 Performance 모델 정리

### what/how

- Festival 도메인 예외를 공통 예외 체계에 맞춰 404·409·422 의미로 구분함.
- Performance 모델에 공통 `DateTimeMixin`을 적용하고 상태값을 Domain `StrEnum`으로 분리함.
- 같은 Festival 안에서 공연 제목이 중복되지 않도록 `(festival_id, title)` 복합 유니크 제약을 추가함.
- Festival Repository 인터페이스를 정의하고 Performance 도메인 구현을 시작함.

### blockers/concerns

- Performance가 Festival 엔티티에 직접 의존하지 않으면서 축제 기간 안의 공연인지 검증해야 했음.
- Repository와 Service 초안은 있었지만 실제 저장·트랜잭션 흐름은 아직 완성되지 않았음.

### resolution

- Festival 객체 대신 시작일·종료일 값을 Performance 규칙에 전달하는 방향으로 의존성을 줄임.
- 병합된 작업과 로컬 초안을 구분해 기록함.

### verification

- Festival 예외 변경 커밋 `06ca85b`, Performance 모델 정리 커밋 `4729b18`을 확인함.
- Festival Repository 인터페이스는 커밋 `58347e0`, PR #64 병합으로 확인함.
- Performance Service·Router는 당시 초안이므로 완성된 API로 보지 않음.

## 2026-11-06 — Performance 도메인 규칙 구현

### what/how

- 프로젝트 ERD를 최신 내용으로 갱신함.
- Performance 엔티티와 도메인 예외를 구현함.
- 공연 일정·예매 기간·수량·가격 검증과 `SCHEDULED`, `OPEN`, `SOLD_OUT`, `CANCELED`, `COMPLETED` 상태 전이를 정의함.
- Festival의 nullable `canceled_at`이 모델·도메인·응답 스키마에서 일관되게 사용되는지 확인함.

### blockers/concerns

- 현재 시각을 엔티티 안에서 직접 만들면 테스트하기 어렵고 상태 전이 결과가 실행 시점에 따라 달라질 수 있었음.
- Festival `canceled_at` 모델 변경은 실제로 11월 4일에 작성된 것이므로 11월 6일 신규 구현과 구분해야 했음.

### resolution

- 상태 전이 메서드가 현재 시각을 인자로 받도록 설계해 테스트에서 시점을 고정할 수 있게 함.
- 규칙을 엔티티 생성·상태 전이 메서드에 모아 Service나 Router가 우회하지 않도록 함.

### verification

- Performance 엔티티·예외·상태 전이는 커밋 `e5972d8`에서 확인함.
- Festival `canceled_at` 모델 변경은 11월 4일 커밋 `dba353a`, `9f95efd`에서 확인함.
- 이 시점에는 전체 테스트나 API 실행 검증 기록이 없어 구현과 검증 완료를 구분함.

## 2026-11-07~08 — 재고 규칙과 Repository·Service 연결

### what/how

- Performance의 잔여 수량 차감·복구와 일정 수정 검증을 추가함.
- Performance Repository 인터페이스에 제목 중복 규칙을 반영하고 모델·스키마를 엔티티 기준으로 정리함.
- SQLAlchemy Repository 구현체를 작성하고 Performance 모델에 `version_id_col` 기반 낙관적 락을 적용함.
- Festival Repository 구현체와 생성·조회·수정·취소 Application Service를 구현함.

### blockers/concerns

- 동시에 재고를 변경할 때 마지막 저장이 이전 변경을 덮는 lost update 가능성이 있었음.
- 도메인 객체와 ORM 모델 사이 변환, `flush`와 `commit` 책임을 어느 계층에 둘지 정리가 필요했음.

### resolution

- Performance의 `version` 컬럼을 SQLAlchemy `version_id_col`로 지정해 저장 시 충돌을 감지하도록 함.
- Repository는 조회·변환·`flush`를 맡고 요청 단위 commit은 공통 DB 흐름에서 처리하는 방향으로 통일함.

### verification

- 재고·일정 규칙은 커밋 `22a3766`, Repository 인터페이스는 `3d243b5`에서 확인함.
- Performance Repository와 낙관적 락은 `c79c1c1`, Festival Repository는 `f9e2efb`에서 확인함.
- 11월 7일 재고 차감 작업은 `py_compile`만 확인된 시점이 있었으므로 전체 동작 검증으로 확대해 기록하지 않음.

## 2026-11-09 — Festival 취소 정책과 Performance API 완성

### what/how

- 취소되지 않은 공연이 있으면 Festival 취소를 409로 막는 정책을 구현함.
- 축제 기간 밖 공연 검사를 전체 목록 조회 대신 `EXISTS` 쿼리로 변경함.
- Performance 생성·목록·상세·수정·오픈·취소·종료·예매 가능 여부 API 8개를 Service → Dependencies → Wiring → Router 순서로 연결함.
- 회의 결정에 맞춰 `/v1`, `Annotated`, `PATCH`, `routers/v1/router.py`, 공용 KST 시간 유틸을 적용함.
- 취소된 Festival에는 새 Performance를 만들 수 없도록 `Festival.ensure_not_canceled()` 규칙을 재사용함.

### blockers/concerns

- 메서드 호출에 `self`를 직접 넘기거나 타입을 값처럼 전달하는 오류가 있었음.
- `Performance.create()`를 거치지 않고 직접 생성해 도메인 검증을 우회할 위험이 있었음.
- Repository·Wiring 복사 과정에서 다른 도메인 저장소나 메서드를 연결하는 오류가 있었음.
- `dev` 병합 과정에서 import와 공용 시간 유틸 충돌을 함께 해결해야 했음.

### resolution

- 엔티티 생성은 항상 `create()`를 거치고, 수정 시 Festival은 요청값이 아니라 기존 `performance.festival_id`로 조회하도록 정리함.
- 현재 시각은 Service가 `now_utc()`로 만들고 엔티티에 전달하도록 책임을 분리함.
- 중복 규칙은 `ensure_...()` 메서드로 모아 Service와 Entity가 같은 검사를 재사용하게 함.
- 후속 범위인 관리자 권한과 예매 일괄 취소는 각각 이슈 #119, #131로 분리함.

### verification

- Docker PostgreSQL 기반 테스트 앱에서 Performance API 20개, Festival API 6개 시나리오가 통과함.
- `uvicorn`과 Swagger에서 Festival·Performance 엔드포인트 등록을 확인함.
- 변경 파일 기준 `ruff`는 통과했으나 프로젝트 전체의 기존 경고와 `main.py` import 경고 1개는 남아 있었음.
- PR #118의 리뷰 반영과 PR #132의 후속 리뷰 상태는 당시 진행 중이므로 병합 완료로 기록하지 않음.

## 2026-11-10 — 관리자 검사와 취소 연쇄 처리

### what/how

- Festival 생성·수정·취소 API와 Performance 생성·수정·오픈·취소·종료 API에 관리자 검사를 추가함.
- Performance 취소 시 관련 활성 예매를 일괄 취소하는 흐름을 구현함.
- Performance Wiring에 Ticket Repository를 연결하고 공용 `CurrentActor`·`get_current_actor` 위치를 정리함.
- Swagger에서 Festival·Performance 관리자 API가 별도 그룹으로 보이도록 문서를 정리함.

### blockers/concerns

- 공연 취소가 예매·티켓·결제에 미치는 범위를 한 트랜잭션 안에서 어디까지 책임질지 조율이 필요했음.
- 관리자 역할값과 실제 접근 차단 로직을 분리해 이해해야 했음.

### resolution

- 역할 Enum은 값 표현에 사용하고, 실제 접근 제한은 인증된 Actor를 검사하는 의존성으로 처리함.
- 공연 취소 흐름에 필요한 Repository를 Wiring에서 조립해 Application Service가 도메인 간 순서를 제어하도록 함.

### verification

- 관리자 검사 커밋 `701683e`, `b6a0fbf`, Swagger 정리 `2c31cc4`를 확인함.
- 예매 일괄 취소는 `caa2e71`, Wiring 수정은 `b8d5878`에서 확인함.
- 커밋 존재는 확인했지만 이 문서에서는 배포·운영 검증까지 완료했다고 보지 않음.

## 2026-11-11 — 프로젝트 문서화와 동시성 설계 정리

### what/how

- README를 카락페 콘셉트로 개편하고 포스터·시연 GIF·프로젝트 설명을 정리함.
- Performance와 Ticket의 낙관적 락, 예약·결제 흐름의 `SELECT ... FOR UPDATE`, 만료 배치의 `SKIP LOCKED` 사용 이유를 코드 기준으로 정리함.
- 관계 로딩은 컬렉션에 `selectinload()`, 단일 객체에 `joinedload()`를 우선 검토한다는 기준을 학습 기록으로 남김.

### blockers/concerns

- `version` 컬럼만 존재하는 것과 SQLAlchemy가 실제 낙관적 락을 수행하도록 `version_id_col`을 설정하는 것은 구분해야 했음.
- 락 방식은 한 가지로 통일하는 문제가 아니라 충돌 시 기다릴지, 실패시킬지, 잠긴 작업을 건너뛸지에 따라 선택해야 했음.

### resolution

- 변경 충돌을 즉시 알리는 Performance·Ticket에는 낙관적 락을 사용함.
- 처리 순서가 중요한 예약·결제에는 비관적 락을, 반복 실행되는 만료 배치에는 `SKIP LOCKED`를 사용한 이유를 구분해 문서화함.

### verification

- README 개편 커밋 `e68500e`, 시연 GIF 추가 커밋 `2979977`을 확인함.
- Performance Repository의 `version_id_col` 적용은 앞선 커밋 `c79c1c1`에서 확인함.
- 문서화와 코드 확인을 수행했으며, 별도의 부하 테스트나 운영 환경 동시성 검증을 완료한 것으로 기록하지 않음.

## AI 이미지 생성 활용 기록

카락페의 프로젝트 콘셉트를 README에서 빠르게 전달하기 위해 ChatGPT의 이미지 생성 기능으로 고양이 락스타 이미지와 메인 포스터를 제작했다. 아래 내용은 생성 당시 남은 이미지 파일과 Git 기록을 기준으로 재구성한 과정이며, 당시의 원문 프롬프트가 그대로 보존된 것은 아니다.

### 1. 이미지가 필요했던 이유

- 백엔드 프로젝트라도 README 첫 화면에서 “락 페스티벌 예매 시스템”이라는 주제를 바로 이해할 수 있게 하고 싶었음.
- 팀명인 카락페(KAROCKFE)와 고양이 락스타 콘셉트를 하나의 시각 언어로 통일할 필요가 있었음.
- 일반적인 기술 문서형 README보다 팀 프로젝트의 개성과 발표·포트폴리오 활용성을 높이고자 했음.

### 2. 프롬프트에 전달한 핵심 조건

이미지 생성 요청은 다음 요소를 조합하는 방식으로 구성했다.

- **주인공:** 검은 고양이 락스타
- **행동과 소품:** 일렉트릭 기타를 연주하거나 들고 있는 모습
- **장르와 분위기:** 펑크 록, 인디 공연 포스터, 에너지 넘치는 무대
- **색상:** 검정·아이보리 바탕에 강한 핫핑크 포인트
- **질감:** 찢은 종이 콜라주, 거친 인쇄, 하프톤, 낡은 포스터 질감
- **문구:** `KANT ROCK FESTIVAL`, `KAROCKFE`
- **사용처와 비율:** README 상단용 가로 배너와 포스터용 세로 이미지

재현용으로 정리한 프롬프트 예시는 다음과 같다. 이는 당시 프롬프트의 복사본이 아니라 결과물을 바탕으로 정리한 템플릿이다.

> 검은 고양이 락스타가 일렉트릭 기타를 연주하는 KANT ROCK FESTIVAL 포스터. 펑크 록 공연 전단지처럼 찢은 종이 콜라주, 거친 스크린 프린트와 하프톤 질감, 검정·아이보리·핫핑크 중심의 강한 대비. KAROCKFE 문구를 크고 읽기 쉽게 배치하고, README에서 사용할 수 있도록 가로 배너 버전과 세로 포스터 버전을 제작한다.

### 3. 생성과 선택 과정

1. 먼저 “고양이 + 락 페스티벌”이라는 프로젝트 콘셉트를 정하고 고양이 락스타 중심의 이미지를 생성함.
2. README 상단에서 잘 보이는 가로형 이미지는 캐릭터와 기타를 오른쪽에 두고 왼쪽 여백을 확보한 배너 구도로 선택함.
3. 프로젝트 소개 하단에 사용할 세로형 포스터는 `KANT ROCK FESTIVAL`과 `KAROCKFE` 문구, 기타를 든 고양이가 한눈에 보이는 구도로 선택함.
4. 두 이미지의 검정·아이보리·핫핑크 색상과 종이 콜라주 질감을 맞춰 같은 브랜드의 결과물처럼 보이게 함.
5. 생성 결과에서 문구의 가독성, 고양이의 형태, 기타의 왜곡, README에서의 크롭 상태를 확인한 뒤 최종 파일을 저장함.

| 변형 제작 | 가로 배너와 세로 포스터 구도 제안 | README에서 필요한 비율과 배치 결정 |
| 문서 구성 | 카락페 분위기에 맞는 README 문구와 섹션 구조 보조 | 실제 기능·기술 스택·실행 방법의 정확성 검토 |
| 결과 검수 | 여러 시각적 후보를 빠르게 생성 | 글자 오류, 형태 왜곡, 가독성, 프로젝트 적합성 검토 |

시연 GIF인 `assets/demo-admin.gif`와 `assets/demo-user.gif`는 실제 동작을 보여 주는 자료로, 생성형 이미지와는 역할이 다르다. 이미지 생성 AI는 프로젝트의 브랜드와 분위기를 표현하는 데 사용했고, 시연 GIF는 구현 결과를 증명하는 용도로 분리했다.

### 6. 다른 팀에 설명할 때의 핵심

- AI에게 단순히 “고양이 그림을 만들어 달라”고 요청한 것이 아니라 **프로젝트 목적, 캐릭터, 장르, 색상, 질감, 문구, 사용 비율**을 구체적으로 전달했다.
- 한 번 생성하고 끝내기보다 README에서 실제로 보이는 크기와 문구 가독성을 기준으로 결과를 골랐다.
- AI는 시각적 초안을 빠르게 만드는 도구로 사용했고, 최종 콘셉트 선택·오류 검수·README 적용은 직접 수행했다.
- 기술 구현을 이미지로 대체하지 않고, 실제 API 시연 GIF와 기술 문서를 함께 제공해 프로젝트 설명력을 보완했다.
