# 2026-11-11 TIL — SQLAlchemy 관계 로딩과 동시성 제어

## 1. 관계 로딩 전략: 컬렉션인가, 단일 객체인가

SQLAlchemy에서 관계를 미리 로딩할 때는 관계의 방향과 조회 결과의 크기를 먼저 봐야 한다.

| 관계 | 기본 선택 | 이유 |
| --- | --- | --- |
| 1:N 컬렉션 | `selectinload()` | JOIN으로 부모 행이 반복되는 것을 피할 수 있다. |
| N:1 단일 객체 | `joinedload()` | 행 증폭이 거의 없어 한 번의 쿼리로 가져오기 좋다. |
| N:M 컬렉션 | `selectinload()` | JOIN 결과가 크게 늘어날 가능성이 높다. |

### 1:N 컬렉션: `selectinload()`

축제 하나가 여러 공연을 가지는 관계라면 다음과 같이 조회할 수 있다.

```python
stmt = select(Festival).options(
    selectinload(Festival.performances)
)
```

개념적으로 SQL은 두 번 실행된다.

```sql
SELECT * FROM festivals;

SELECT * FROM performances
WHERE festival_id IN (1, 2, 3);
```

첫 번째 쿼리에서 부모인 축제를 조회하고, 두 번째 쿼리에서 축제 ID 목록에 해당하는 공연을 한꺼번에 조회한다. 부모마다 자식을 따로 조회하는 N+1 문제를 피하면서 JOIN에 의한 부모 행 반복도 줄일 수 있다.

### N:1 단일 객체: `joinedload()`

공연 여러 개가 각각 하나의 축제를 참조하는 관계라면 다음과 같이 조회할 수 있다.

```python
stmt = select(Performance).options(
    joinedload(Performance.festival)
)
```

개념적으로는 한 번의 JOIN 쿼리가 실행된다.

```sql
SELECT performances.*, festivals.*
FROM performances
LEFT JOIN festivals
    ON performances.festival_id = festivals.id;
```

각 공연에 연결되는 축제는 하나뿐이므로 컬렉션 JOIN처럼 결과 행이 크게 늘어나지 않는다.

### 1:N에서 `joinedload()`가 불리할 수 있는 이유

Festival A에 Performance가 100개 있으면 JOIN 결과에는 Festival A의 데이터도 100번 반복된다.

```text
Festival A | Performance 1
Festival A | Performance 2
Festival A | Performance 3
...
```

SQLAlchemy 2.x에서 컬렉션을 `joinedload()`한 결과는 부모 객체를 중복 제거하기 위해 보통 `unique()`도 호출해야 한다.

```python
result = await session.execute(
    select(Festival).options(
        joinedload(Festival.performances)
    )
)

festivals = result.unique().scalars().all()
```

따라서 다음을 안전한 기본값으로 기억하면 된다.

> 컬렉션(1:N, N:M)은 `selectinload()`, 단일 객체(N:1, 1:1)는 `joinedload()`를 먼저 고려한다.

다만 절대 규칙은 아니다. 부모 한 건만 조회하고 자식 수도 매우 적다면 1:N에서도 `joinedload()`가 더 단순하고 빠를 수 있다. 실제 데이터 크기, 쿼리 수, 네트워크 비용을 보고 결정해야 한다.

## 2. 동시성 제어: 낙관적 락과 비관적 락

`positive lock`, `negative lock`은 일반적인 데이터베이스 용어가 아니다. 보통 비교하는 용어는 **optimistic lock(낙관적 락)**과 **pessimistic lock(비관적 락)**이다. 우리 프로젝트는 두 방식을 모두 사용한다.

### 낙관적 락: 저장할 때 버전을 확인한다

낙관적 락은 충돌이 자주 일어나지 않을 것이라고 보고 작업 중에는 행을 잠그지 않는다. 대신 저장할 때 내가 처음 읽었던 버전이 여전히 최신인지 검사한다.

우리 프로젝트에서는 `Performance`와 `Ticket` 모델의 `version` 컬럼을 SQLAlchemy의 `version_id_col`로 지정했다.

| 도메인 | 설정 위치 | 충돌 시 예외 |
| --- | --- | --- |
| Performance | `src/performances/infrastructure/models.py` | `PerformanceVersionConflict` → 409 |
| Ticket | `src/tickets/infrastructure/models.py` | `TicketVersionConflict` → 409 |

```python
version: Mapped[int] = mapped_column(
    Integer,
    default=1,
    nullable=False,
)

__mapper_args__ = {"version_id_col": version}
```

동작 흐름은 다음과 같다.

1. 데이터를 읽을 때 현재 `version`도 함께 가져온다.
2. 저장할 때 처음 읽은 버전과 현재 버전을 비교한다.
3. 같으면 UPDATE하고 버전을 1 증가시킨다.
4. 다르면 다른 요청이 먼저 수정한 것이므로 409 충돌 응답을 반환한다.

SQLAlchemy가 보내는 UPDATE는 개념적으로 다음과 같다.

```sql
UPDATE performances
SET remaining_count = 9,
    version = 2
WHERE id = 1
  AND version = 1;
```

`WHERE version = 1`에 맞는 행이 없다면 이미 다른 트랜잭션이 수정한 것이다. SQLAlchemy의 `StaleDataError`를 프로젝트의 충돌 예외로 바꾸어 클라이언트에 409로 전달한다.

#### Performance에 필요한 이유

`remaining_count`는 예약과 취소 과정에서 `decrease_remaining()` 또는 `increase_remaining()`으로 바뀐다. 두 요청이 동시에 "좌석 10개 남음"을 읽고 각각 9로 저장하면 한 요청의 변경이 사라지는 lost update가 생길 수 있다. 버전이 다르면 두 번째 저장을 실패시켜 이를 막는다. 공연 수정·오픈·취소·종료처럼 같은 공연 행을 갱신하는 흐름에도 같은 검사가 적용된다.

#### Ticket에 필요한 이유

같은 티켓에 취소 같은 상태 변경 요청이 동시에 들어오면 먼저 저장한 요청만 성공하고, 이전 버전을 가진 나머지 요청은 충돌 처리된다.

낙관적 락의 핵심은 **기다리지 않고 저장 시점에 충돌을 발견한다**는 것이다. 따라서 409를 받은 호출자는 최신 데이터를 다시 읽고 재시도할지 결정해야 한다.

### 비관적 락: 먼저 행을 잠근 뒤 처리한다

비관적 락은 충돌 가능성이 있거나 상태 변경 순서가 중요한 경우 먼저 대상 행을 잠근다. PostgreSQL에서는 `SELECT ... FOR UPDATE`를 사용한다.

```python
stmt = (
    select(ReservationModel.id)
    .where(ReservationModel.id == reservation_id)
    .with_for_update()
)
```

한 트랜잭션이 행을 잠그고 있으면 같은 행을 `FOR UPDATE`로 조회하는 다른 트랜잭션은 첫 번째 트랜잭션이 commit 또는 rollback할 때까지 기다린다.

#### 일반 `FOR UPDATE`: 순서를 기다린다

| 위치 | 사용 흐름 | 목적 |
| --- | --- | --- |
| `reservations/infrastructure/repositories.py`의 `lock()` | 예약 취소·확정·결제 실패 해제, 티켓 취소 | 같은 예약의 상태 변경을 한 번에 하나씩 처리한다. |
| `payments/infrastructure/sqlalchemy_repository.py`의 `lock_reservation()` | 결제 승인·취소·웹훅·복구 | 같은 예약의 결제 승인과 취소가 겹치지 않게 한다. |
| 결제 저장소의 `save()` | 기존 결제 갱신 | 결제 행을 잠그고 최신 상태를 확인한 뒤 저장한다. |
| 예약 저장소의 `find_active_by_festival_for_update()` | 공연·축제 취소 시 활성 예약 일괄 취소 | 대상 예약을 잠근 뒤 최신 상태를 다시 검사한다. |

결제 저장은 단순한 비관적 락에서 한 단계 더 나아간다. 결제 행을 `FOR UPDATE`로 잠근 뒤, 최초 조회 때 만든 `persistence_token`과 최신 행의 상태 지문을 비교한다. 서로 다르면 오래된 상태를 덮어쓰지 않고 `PaymentConcurrentUpdate` 409를 발생시킨다. 즉 **행 잠금과 충돌 감지를 함께 사용하는 방식**이다.

#### `FOR UPDATE SKIP LOCKED`: 잠긴 행은 건너뛴다

```python
stmt = (
    select(ReservationModel)
    .where(...)
    .with_for_update(skip_locked=True)
)
```

| 위치 | 사용 흐름 | 목적 |
| --- | --- | --- |
| 예약 저장소의 `find_overdue_pending()` | 예약 만료 배치 | 결제 확정 중인 예약은 이번 실행에서 건너뛴다. |
| 티켓 저장소의 `find_all_to_expire()` | 티켓 만료 배치 | 취소 등으로 처리 중인 티켓은 이번 실행에서 건너뛴다. |

백그라운드 만료 작업은 주기적으로 다시 실행된다. 지금 잠긴 행을 기다리며 전체 작업을 지연시키기보다 건너뛰고 다음 실행에서 다시 확인하는 편이 적합하다.

## 3. 오늘의 정리

- 관계 로딩은 **컬렉션이면 `selectinload()`, 단일 객체면 `joinedload()`**를 기본 선택으로 삼되 데이터 크기에 따라 조정한다.
- 낙관적 락은 작업 중 잠그지 않고 **저장 시 버전 충돌을 검사**한다. 우리 프로젝트의 Performance와 Ticket이 사용한다.
- 비관적 락은 **상태 변경 전에 행을 잠가 작업 순서를 보장**한다. 예약과 결제 흐름이 사용한다.
- 주기적으로 다시 실행되는 만료 배치는 잠긴 행을 기다리지 않는 `SKIP LOCKED`가 잘 맞는다.
- 한 도메인에 반드시 한 가지 방식만 써야 하는 것은 아니다. 결제 저장처럼 행 잠금과 상태 지문 비교를 함께 사용할 수도 있다.

> 로딩 전략은 "조회 결과가 얼마나 불어나는가"를 보고, 락 전략은 "충돌 시 기다릴 것인가 실패시킬 것인가"를 보고 선택한다.
