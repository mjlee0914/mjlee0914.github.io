:bulb: chunk vs embed vs vectorize

```
긴 문서 ──[chunk]──▶ 조각들 ──[embed]──▶ 의미 벡터들 ──▶ 벡터 DB
                              └── embed는 vectorize의 한 종류
```

- vectorize가 더 넓은 범위
- embed는 그 중 하나
- vectorizing methods:
  - One-hot: 단어마다 칸 하나를 1로 표시
  - Bag of words, TF-IDF: 단어가 몇 번 나왔는지 세기
  - Embedding: 신경망 모델이 의미를 학습해서 숫자로 변환

## 1. 임베딩과 벡터 유사도

### 임베딩

- 임베딩: **실수 벡터**로 바꿈
- 의미가 비슷한 텍스트일수록 벡터 공간에서 가까이 놓임
- 단어가 안 겹쳐도 의미가 비슷하면 검색됨

```text
"강아지" → [0.21, -0.53, 0.88, ...]
"고양이" → [0.19, -0.48, 0.91, ...]   ← 가까움
"자동차" → [-0.72, 0.33, -0.10, ...]  ← 멂
```

- 임베딩 전에 문장을 토큰 단위로 쪼개고 ID를 붙이는 **토큰화(Tokenization)** 를 거침
- RAG에서는 단어 하나가 아니라 **chunk(문장·문단) 하나를 벡터 하나로** 만드는 경우가 대부분임
  - (RAG에서 검색해서 LLM에게 넘겨줄 단위가 문단임)
  - (단어 단위로 만들면 검색 결과가 단어 조각으로 나옴)

### 벡터 공간 측정법

|                | 유클리드 거리          | 코사인 유사도             |
| -------------- | ---------------------- | ------------------------- |
| 보는 것        | 두 점 사이의 직선 거리 | 두 벡터 사이의 각도(방향) |
| 비슷할수록     | 값이 작다 (0이면 같음) | 값이 크다 (-1 ~ 1)        |
| 벡터 길이 영향 | 받는다                 | 받지 않는다               |

- ex) "고양이 귀여워" 와 "고양이 너무너무 귀여워 진짜 귀여워" 두 문장 가정
- 유클리드 거리는 길이를 보기 때문에 두 문장이 다르다고 판단
- 코사인 유사도는 방향을 보기 때문에 두 문장이 매우 비슷하다고 판단

### 정규화된 벡터라면 둘은 같다

정규화하면 모든 벡터 길이가 1이 되므로 다음 식이 성립한다.

$$
\|A - B\|^2 = 2 - 2\cos\theta
$$

유클리드 거리가 코사인 유사도만으로 결정되므로 **검색 순위가 완전히 같다.** 100장짜리 논문과 3장짜리 논문의 길이 차이는 측정법이 아니라 **chunking**으로 해결한다. 문서 전체를 벡터 하나로 만들지 않고 비슷한 크기의 chunk로 나눠서 각각 임베딩한다.

## 2. Chunking

### 왜 쪼갬?

1. **노이즈**: 질문과 관련 없는 내용이 섞이면 답변이 흐려지고 hallucination이 생길 수 있다. LLM은 긴 입력의 중간을 놓치는 경향(**Lost in the middle**)도 있다.
2. **Context window**: LLM과 임베딩 모델 모두 입력 토큰 한도가 있다. 입력이 길수록 비용과 응답 시간도 늘어난다.
3. **검색 정확도**: 긴 텍스트를 벡터 하나로 만들면 여러 주제가 평균내져 흐릿한 벡터가 된다.

### chunk 크기의 트레이드오프

- **너무 크면 → 노이즈**: chunk 하나에 여러 주제가 섞인다.
- **너무 작으면 → 누락(맥락 손실)**: 하나의 정보가 여러 chunk로 갈라져서 top-k 검색에 일부만 걸린다. `"F학점이 없어야 합니다."`만 떨어져 있으면 무엇의 조건인지 알 수 없다.
- 그래서 앞 chunk의 끝부분을 다음 chunk에 겹쳐 넣는 `chunk_overlap`을 둔다.

### CharacterTextSplitter

```python
CharacterTextSplitter(separator="", chunk_size=30, chunk_overlap=10)
```

```text
[0번째 - 제1조 (목적)\n본 규정은 장학금 지급 기준을 정의합니]
[1번째 - 급 기준을 정의합니다.\n\n제2조 (선발 기준)\n직전 학]
```

- `separator=""`는 한 글자 단위로 자르라는 뜻이다. 공백과 `\n`도 한 글자로 센다.
- 다음 chunk는 이전 chunk의 마지막 10글자(`급 기준을 정의합니`)를 다시 포함해서 시작한다.
- 글자 수만 보기 때문에 `정의합니|다`처럼 **단어 중간에서 잘린다.**
- `separator="\n\n"`처럼 구분자를 주면 문단 단위로 자르지만, 문단 하나가 `chunk_size`보다 길면 더 쪼개지 않는다.

### RecursiveCharacterTextSplitter

구분자 목록을 **큰 단위부터 순서대로** 시도한다. 기본값은 `["\n\n", "\n", " ", ""]`이다. 먼저 문단으로 나누고, `chunk_size`보다 큰 조각만 다음 구분자로 다시 나눈다. 의미 단위를 최대한 지키면서 크기도 지킬 수 있다.

```python
separators=["##", "###"]  # ❌
```

- `"##"`는 `"###"` 안에도 들어 있어서 첫 단계에서 `###` 제목까지 이미 잘린다.
- 마지막 대비책이 없어서 `###`로도 줄일 수 없는 조각은 `chunk_size`를 넘긴 채 남는다.

```python
separators=["\n## ", "\n### ", "\n\n", "\n", " ", ""]  # ✅
```

### MarkdownHeaderTextSplitter

|             | RecursiveCharacterTextSplitter | MarkdownHeaderTextSplitter                 |
| ----------- | ------------------------------ | ------------------------------------------ |
| 자르는 기준 | 크기 (`chunk_size`)            | 제목 구조 (`#`, `##`, `###`)               |
| 결과        | 문자열 리스트                  | `Document` 리스트 (제목이 metadata로 붙음) |
| 크기 제한   | 있음                           | 없음                                       |

`MarkdownHeaderTextSplitter`는 `chunk_size`, `chunk_overlap`, `separators`를 받지 않는다. 제목 기준으로 먼저 나누고, Recursive splitter로 긴 섹션의 크기를 줄이는 식으로 **두 개를 이어서** 쓴다.

### metadata

LangChain의 `Document`는 본문과 꼬리표로 구성된다.

```python
Document(
    page_content="평점 3.5 이상이어야 하며 F학점이 없어야 합니다.",  # 임베딩·검색 대상
    metadata={"h2": "장학금", "h3": "선발 기준"},                  # 부가 정보
)
```

- metadata는 출처 및 부가 정보를 키값 형태의 dict로 관리함.
- `source`, `page`, 섹션 제목, 작성일 같은 정보를 넣어 두면 출처 표시 및 검색 결과 필터링 가능

## 3. Document Loader

- **BeautifulSoup4 (`bs4`)**: HTML 파싱 라이브러리다. 웹페이지에서 메뉴, 광고, 푸터 같은 노이즈를 걷어내고 본문만 남긴다. 이름은 엉망인 HTML을 부르는 "tag soup"와 『이상한 나라의 앨리스』의 노래 "Beautiful Soup"에서 왔다. `bs4`는 버전 4라는 뜻이다.
- **PyMuPDFLoader**: PDF를 **페이지당 Document 1개**로 만든다. metadata에 `source`, `page`(0부터 시작), `total_pages` 등이 자동으로 들어간다.
- 웹 로더 출력이 앞부분만 보여도 전부 불러온 것일 수 있다. VS Code 노트북은 긴 출력을 잘라서 보여 준다. `len(text)`나 `text[-500:]`로 확인한다.

## 4. RAG 프롬프트

```python
prompt = ChatPromptTemplate.from_messages([   # 튜플 하나가 아니라 리스트로 넘긴다
    ("system", "제공된 [참고 문서]에만 근거하여 답변하세요. ..."),
    ("human", "[참고 문서]\n{context}\n\n[질문]\n{question}"),
])
```

- `from_messages`에 튜플 하나를 그대로 넘기면 system 역할로 인식되지 않는다.
- "참고 문서에만 근거하라"고 지시해도 `{context}`, `{question}` 변수가 없으면 모델은 문서를 받지 못한다.

+) RAG in Big Tech

LLM의 지식 시점(knowledge cutoff) 한계와 hallucination을 해결하려고 쓴다. 원래 RAG 논문(Lewis et al., 2020)은 Facebook AI Research에서 나왔고, Meta는 벡터 검색 라이브러리 **FAISS**도 만들었다. 초보 프로젝트로는 LangChain + OpenAI 임베딩 + `InMemoryVectorStore`로 학칙 같은 내 문서를 검색하는 Q&A 봇부터 만들어 보면 좋다.

### MINI PROJECT IDEA: 내 TIL 블로그에 RAG 검색 붙이기

RAG를 배우면서 지금까지 쓴 TIL과 프로젝트 글을 RAG 데이터로 써서 블로그에 검색 기능을 넣으면 어떨까 하는 생각이 들었다. Codex와 이야기하면서 구조와 진행 순서를 잡았다.

### 의미 검색과 RAG는 다르다

|           | 의미 검색                                   | RAG 답변                                         |
| --------- | ------------------------------------------- | ------------------------------------------------ |
| 입력 예시 | `낙관적 락`                                 | `우리 프로젝트에서 낙관적 락을 어떻게 적용했지?` |
| 하는 일   | 임베딩 유사도로 관련 문단을 순위대로 찾는다 | 찾은 문단을 근거로 LLM이 답변을 만든다           |
| 결과      | 글 제목, 관련 문단, 링크, 유사도            | 답변과 출처 링크                                 |
| 비용      | 임베딩만 든다                               | LLM 호출 비용이 추가된다                         |

"키워드를 넣으면 관련 글이 쫙 나오는 기능"은 엄밀히 말하면 RAG가 아니라 **의미 검색**이다.
검색을 먼저 제대로 만들고, 그 위에 생성을 올리는 순서가 안정적이다.

- 왜냐하면:
- 생성은 검색 위에 올라가는 단계다. 즉 검색을 기반으로 답변 생성이 된다.
- RAG 답변의 품질은 검색 품질을 넘을 수 없다.
- `질문 -> 검색 -> 관련 문단 -> 생성 -> 답변`

### 전체 구조

```text
TIL·프로젝트 Markdown
  → 로딩 (front matter와 본문 분리)
  → 헤딩 기준 청킹
  → 임베딩
  → 벡터 DB (처음에는 Chroma, 배포할 때는 pgvector)
  → FastAPI 검색 API (/api/search, /api/ask)
  → Hybrid Search (BM25 + 벡터 + RRF) → Re-ranking
  → 블로그 검색 UI에 결과와 원문 링크 표시
```

기술 블로그에는 Hybrid Search가 잘 맞는다. `version_id_col`처럼 정확한 기술명은 BM25가 잘 찾고, "예약할 때 재고 충돌을 막는 방법" 같은 자연어 질문은 벡터 검색이 잘 찾는다.

### 활용 방안

**1. 수업 진도 = 프로젝트 마일스톤**

강의를 따로 듣고 프로젝트를 따로 하지 않는다. 강의 하나가 끝날 때마다 배운 내용을 `til-blog-rag`에 기능 하나로 붙이고 커밋한다.

| 수업                  | 프로젝트에 붙일 기능            | 완료 기준                                               |
| --------------------- | ------------------------------- | ------------------------------------------------------- |
| 2장 1강 문서 로딩     | Markdown 로더                   | front matter와 본문이 분리되고 테스트가 통과한다        |
| 2장 2~3강 청킹        | 헤딩 기준 청커와 전략 비교      | 고정 길이·문단·헤딩 기준 결과를 비교해 기록한다         |
| 2장 4~7강 임베딩·저장 | 인덱싱 스크립트                 | 명령 하나로 전체 인덱싱이 되고, 바뀐 글만 다시 처리한다 |
| 3장                   | `/api/search`, `/api/ask`       | 질문하면 답변과 블로그 URL이 나온다                     |
| 4~5장                 | BM25, Hybrid Search, Re-ranking | 기술명 검색과 자연어 검색이 둘 다 잘 된다               |
| 6~7장                 | 평가셋과 RAGAS                  | 코드를 바꾼 뒤 검색 품질이 떨어졌는지 확인할 수 있다    |

**2. TIL 쓰는 습관이 곧 데이터 품질이다**

내 TIL이 RAG의 원본 데이터가 되므로, 글을 쓰는 방식이 검색 품질을 직접 결정한다.

- **front matter = metadata**: `title`, `date`, `tags`, `description`이 그대로 chunk metadata가 된다. tags를 일관되게 달아야 "SQLAlchemy 태그만 검색" 같은 필터링이 된다.
- **`##` 헤딩 = chunk 경계**: 헤딩 기준으로 청킹하므로 섹션 하나에 주제 하나만 쓴다. 오늘 배운 "chunk가 너무 크면 노이즈"가 그대로 적용된다.
- **front matter 형식 통일**: 지금 TIL 중에는 front matter가 있는 글(261102, 261103, 261113)과 없는 글(261104~261109 작업일지)이 섞여 있다. 로더가 둘 다 처리하게 만들거나 형식을 통일해야 한다.
- 파일명이 `_posts/YYYY-MM-DD-slug.md`가 아니라 `YYMMDD_TIL.md`이므로, 날짜와 URL을 만드는 규칙을 로더에서 정해야 한다.

**3. ax_study에서 한 질문을 평가셋으로 쓴다**

오늘 수업 중에 했던 질문들이 실제 사용자 질문 데이터가 된다. 질문과 "이 질문에는 이 글이 나와야 한다"는 정답을 짝지어 평가셋을 만든다.

```json
{
  "question": "정규화된 벡터에서 유클리드 거리와 코사인 유사도는 뭐가 달라?",
  "expected_sources": ["261113_TIL"],
  "expected_keywords": ["2 - 2cosθ", "검색 순위가 같다"]
}
```

글이나 검색 로직을 바꾼 뒤 같은 질문으로 다시 돌려 보면, 검색 품질이 나빠졌는지 확인하는 회귀 테스트가 된다.

**4. 포트폴리오 프로젝트**

강의 실습을 따라 한 결과물이 아니라, **내 데이터로 청킹·메타데이터 설계·Hybrid Search·평가·증분 갱신까지** 다 해 본 프로젝트가 된다. README 로드맵은 수업 목차가 아니라 기능 단위(문서 수집 → 인덱스 구축 → 검색 MVP → RAG 답변 → 검색 고도화 → 평가 → 블로그 연동·배포)로 쓰고, 단계마다 완료 기준을 적는다.
