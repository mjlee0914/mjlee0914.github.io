## 2. 5장 6강: 질의 유형별 검색 결과 비교

검색 방식은 모든 질문에 동일하게 잘 작동하지 않는다. 질문의 표면적인 단어와 실제 의도를 함께 보고 검색기를 선택해야 한다.

| 질의 유형   | 예시                                    | 주요 위험                                           | 우선 고려할 검색 방식           |
| ----------- | --------------------------------------- | --------------------------------------------------- | ------------------------------- |
| 고유명사형  | `ERR-4012의 원인은?`                    | 임베딩 과정에서 코드·이름의 구별력이 약해질 수 있음 | BM25 또는 Hybrid Search         |
| 의미 탐색형 | `비 오는 날 먹기 좋은 얼큰한 음식`      | 정확히 같은 단어가 없어 BM25가 놓칠 수 있음         | Vector Search                   |
| 복합 조건형 | `2024년 수습 사원의 재택근무 지원 조건` | 의미 유사도만으로 연도·신분 조건을 놓칠 수 있음     | Hybrid Search와 메타데이터 필터 |

### BM25와 벡터 검색의 실패 메커니즘

- **BM25**는 질의와 문서의 단어 일치에 강하다. 고유명사, 제품명, 오류 코드처럼 정확한 문자열이 중요한 질의에 유리하지만 동의어나 우회 표현에는 약하다.
- **벡터 검색**은 표현이 달라도 의미가 유사한 문서를 찾는 데 강하다. 반면 연도, 코드, 부정 표현처럼 작은 차이가 중요한 경우에는 주제만 비슷한 문서를 반환할 수 있다.
- **Hybrid Search**는 두 결과를 결합해 각 방식의 약점을 줄인다. 다만 결합 가중치가 고정되면 특정 질의 유형에 편향될 수 있다.

검색 결과를 비교할 때는 단순히 상위 문서가 그럴듯한지만 보지 않는다. 정답 근거가 포함되었는지, 무관한 문서가 얼마나 섞였는지, 필수 조건이 누락되었는지를 함께 확인해야 한다.

## 3. 5장 7강: 검색 전략 선택과 동적 라우팅

**Query Routing**
질문의 특성을 먼저 분류한 뒤 적합한 검색기로 보내는 조건부 분기

```text
사용자 질문
    │
    ├─ 정확한 이름·코드 중심 ──────> BM25
    ├─ 자연어 의미·의도 중심 ─────> Vector Search
    └─ 의미 + 날짜·조건 복합 ─────> Hybrid Search + Metadata Filter
```

LLM을 라우터로 사용할 때는 자유로운 설명문보다 구조화된 출력을 받는 편이 안전하다.

```python
from typing import Literal
from pydantic import BaseModel

class RouteDecision(BaseModel):
    strategy: Literal["bm25", "vector", "hybrid"]
    reason: str
```

라우팅 정확도만 높다고 전체 품질이 보장되지는 않는다. 분류 비용과 지연 시간이 추가되고, 잘못 분류된 질문은 처음부터 부적절한 검색기로 전달된다. 따라서 고정된 질의 세트로 **라우팅 전후의 검색 지표**를 비교해야 한다.

## 4. 6장: RAG 평가 이론

### 4.1 검색 평가: Precision, Recall, F1

검색 평가는 관련 문서를 얼마나 정확하고 빠짐없이 가져왔는지를 측정한다.

| 지표              | 계산식                                             | 확인하는 질문                                         |
| ----------------- | -------------------------------------------------- | ----------------------------------------------------- |
| Precision(정밀도) | `검색된 관련 문서 수 ÷ 검색된 전체 문서 수`        | 가져온 문서 중 실제로 관련 있는 문서는 얼마나 되는가? |
| Recall(재현율)    | `검색된 관련 문서 수 ÷ 실제로 필요한 관련 문서 수` | 필요한 문서를 얼마나 빠짐없이 가져왔는가?             |
| F1                | `2 × (Precision × Recall) ÷ (Precision + Recall)`  | 정밀도와 재현율의 균형은 어떠한가?                    |

**공식 (TP / FP / FN 표기)**

- **TP (True Positive)**: 검색했고 실제로 관련 있는 문서
- **FP (False Positive)**: 검색했지만 관련 없는 문서
- **FN (False Negative)**: 관련 있지만 검색하지 못한 문서

$$
\text{Precision} = \frac{TP}{TP + FP}
$$

$$
\text{Recall} = \frac{TP}{TP + FN}
$$

$$
F_1 = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}} = \frac{2TP}{2TP + FP + FN}
$$

> F1은 Precision과 Recall의 **조화평균**이다. 산술평균과 달리 둘 중 하나라도 낮으면 F1도 크게 낮아진다.

예를 들어 관련 문서 3개와 무관한 문서 2개를 검색했고, 실제로 필요한 관련 문서가 총 4개였다면 다음과 같다.

```text
Precision = 3 ÷ 5 = 0.60
Recall    = 3 ÷ 4 = 0.75
F1        = 2 × (0.60 × 0.75) ÷ (0.60 + 0.75) ≈ 0.67
```

| 상황                                         | Precision | Recall | 해석                 |
| -------------------------------------------- | --------: | -----: | -------------------- |
| 필요한 문서만 가져왔지만 일부를 놓침         |      높음 |   낮음 | 검색 범위가 좁음     |
| 필요한 문서는 모두 있지만 무관한 문서도 많음 |      낮음 |   높음 | 후보가 과도하게 넓음 |
| 필요한 문서를 빠짐없이 정확히 가져옴         |      높음 |   높음 | 이상적인 검색 결과   |

#### Precision과 Recall의 Trade-off

Precision과 Recall은 보통 **한쪽을 올리면 다른 쪽이 내려가는** trade-off 관계다. 그물에 비유하면 그물을 넓게 던질수록 잡고 싶은 물고기를 놓치지 않지만(Recall↑), 쓸모없는 것도 함께 걸린다(Precision↓). 그물을 좁게 던지면 걸린 것은 대부분 원하는 물고기지만(Precision↑), 놓치는 물고기가 많아진다(Recall↓).

RAG에서 이 그물의 크기를 정하는 손잡이는 주로 **top-k**(가져올 문서 수)와 **유사도 임계값(threshold)** 이다.

| 조정                      | TP / FP / FN 변화                    | Precision | Recall |
| ------------------------- | ------------------------------------ | :-------: | :----: |
| k↑ 또는 threshold↓ (넓게) | FN은 줄지만 FP가 늘어남              |     ↓     |   ↑    |
| k↓ 또는 threshold↑ (좁게) | FP는 줄지만 놓치는 문서(FN)가 늘어남 |     ↑     |   ↓    |

공식으로 보면 이유가 드러난다. Recall의 분모 `TP + FN`은 **정답 문서 총수로 고정**되어 있으므로 많이 가져올수록 Recall은 줄어들지 않는다. 반면 Precision의 분모 `TP + FP`는 **가져온 문서 수 자체**라서, 뒤쪽 순위의 관련 없는 문서가 섞일수록 Precision이 떨어진다.

관련 문서가 총 4개인 상황에서 k만 바꿔 보면 다음과 같다.

| top-k | 가져온 관련 문서(TP) | Precision | Recall |  F1  |
| :---: | :------------------: | :-------: | :----: | :--: |
|   2   |          2           |   1.00    |  0.50  | 0.67 |
|   5   |          3           |   0.60    |  0.75  | 0.67 |
|  10   |          4           |   0.40    |  1.00  | 0.57 |

k를 늘릴수록 Recall은 1.0을 향해 오르지만 Precision은 계속 떨어진다. F1은 이 둘의 균형점을 하나의 숫자로 보여 주므로, **어느 k가 적당한지** 비교할 때 기준으로 쓸 수 있다.

**RAG에서의 실전 판단**

- **Recall을 우선하는 경우**: 정답 근거가 문맥에 아예 없으면 LLM은 정답을 만들 수 없다. 그래서 검색 1단계에서는 k를 넉넉히 잡아 Recall을 확보하는 경우가 많다.
- **Precision을 챙겨야 하는 이유**: 무관한 문서가 많으면 토큰 비용과 지연 시간이 늘고, LLM이 잘못된 문서를 근거로 삼아 답변 품질이 떨어질 수 있다.
- **둘을 함께 잡는 패턴**: 1단계에서 넓게 검색해 Recall을 확보하고(예: k=20), 2단계에서 **reranker**로 상위 몇 개만 남겨 Precision을 끌어올린다(예: top-3).

RAGAS의 `ContextPrecision`과 `ContextRecall`은 이 관점을 LLM 기반 문맥 평가에 적용한다.

### 4.2 생성 평가: Faithfulness와 Answer Relevancy

- **Faithfulness**: 답변의 주장들이 검색 문맥에서 근거를 찾을 수 있는가.
- **Answer Relevancy**: 답변이 사용자의 질문 의도에 직접 답하는가.

두 지표는 서로 독립적이다. 문서에 있는 사실만 말해도 질문과 무관하면 관련성이 낮고, 질문에 자연스럽게 답해도 문서에 없는 내용을 덧붙이면 사실성이 낮다.

### 4.3 검색 실패와 생성 실패를 분리해야 하는 이유

| 검색 문맥      | 생성 답변      | 진단 방향                          |
| -------------- | -------------- | ---------------------------------- |
| 정답 근거 없음 | 오답           | 청킹, 임베딩, 필터, 검색 전략 점검 |
| 정답 근거 있음 | 오답 또는 환각 | 프롬프트와 생성 모델 점검          |
| 정답 근거 있음 | 정답           | 정상 사례                          |

검색 문맥에 정답이 없는데 생성 모델만 수정하면 근본 원인이 남는다. 반대로 검색이 정상인데 검색기만 계속 조정하면 생성 단계의 환각을 해결할 수 없다.

## 5. 7장 1·2강: 평가셋 설계와 구축

### 골든셋의 세 요소

`12_rag/chapter06_07/06_01.ipynb`

- Pydantic 모델로 평가 샘플의 구조를 고정

```python
class RagEvalSample(BaseModel):
    user_input: str
    reference: str
    retrieved_contexts: list[str]
```

- `user_input`: 실제 사용자가 입력할 법한 질문
- `reference`: 근거 문서만으로 작성한 모범 정답
- `retrieved_contexts`: 정답을 도출하는 데 필요한 원본 문서

코드에서는 단순 사실 확인, 여러 문서를 결합하는 복합 추론, 문서 밖 정보를 묻는 함정 질문을 생성하도록 프롬프트를 구성했다. 이 세 유형을 섞는 이유는 단순 검색 성공뿐 아니라 조합 능력과 환각 억제 능력까지 확인하기 위해서다.

### LLM 생성 평가셋의 주의점

LLM은 평가 데이터 제작을 보조할 수 있지만 자동 생성 결과가 곧 정답은 아니다.

1. 질문이 실제 문서에서 답할 수 있는지 확인한다.
2. 모범 정답에 문서 밖 지식이 들어가지 않았는지 확인한다.
3. 근거 문서 목록이 정답의 모든 주장을 뒷받침하는지 확인한다.
4. 질문 유형과 난이도가 한쪽으로 치우치지 않았는지 확인한다.
5. 결측치와 중복을 검사한 뒤 CSV 등 재사용 가능한 형식으로 고정한다.

11/19 복합 추론 예시는 원격 근무 규정과 수습 사원 제한 규정을 함께 사용한다. 함정 질문에는 문서에 없는 내용을 추측하지 않고 “제공된 문서에 나와 있지 않다”는 모범 답안을 둔다.

```python
metrics = [
    Faithfulness(llm=evaluator_llm),
    ResponseRelevancy(
        llm=evaluator_llm,
        embeddings=evaluator_embeddings,
    ),
]
```

실행 결과는 다음과 같았다.

| 사례                                  | Faithfulness | Answer Relevancy | 해석                                      |
| ------------------------------------- | -----------: | ---------------: | ----------------------------------------- |
| 문서에 근거한 주말 운영 답변          |          1.0 |           0.5928 | 사실성은 높지만 관련성 임계값에 근접      |
| 문서에 없는 24시간 개방을 추가한 답변 |          0.5 |           0.6529 | 질문에는 답했지만 근거 없는 주장이 포함됨 |

평균 점수만 보면 실패 사례가 가려질 수 있으므로 행 단위 점수를 확인해야 한다. 또한 단일 임계값 `0.6`은 실습용 기준일 뿐이다. 실제 임계값은 사람이 판정한 검증 데이터와 비용을 바탕으로 조정해야 한다.

## 8. 7장 5강: 검색 실패 분석

검색 실패는 대표적으로 다음 세 범주에서 발생한다.

| 실패 유형              | 증상                                                  | 개선 방향                                    |
| ---------------------- | ----------------------------------------------------- | -------------------------------------------- |
| 청킹 실패              | 정답 문장이 경계에서 잘리거나 관련 정보가 서로 분리됨 | chunk size·overlap 조정, 문서 구조 기반 분할 |
| 임베딩·어휘 불일치     | 의미 또는 고유명사를 적절히 표현하지 못함             | 임베딩 모델 점검, BM25·Hybrid Search 병행    |
| 메타데이터 필터링 실패 | 다른 연도·부서·문서 버전이 검색됨                     | 메타데이터 스키마 보강, 필터 조건 검증       |

`12_rag/chapter06_07/07_05.ipynb`

- 임계값을 `0.8`로 두고 Context Precision 또는 Recall이 낮은 사례만 골라 만든 LLM 진단 레포트

```python
failed_cases = df_result[
    (df_result["context_precision"] < 0.8)
    | (df_result["context_recall"] < 0.8)
]
```

당일 결과에서 2024년 장학금 질문에 2023년 문서가 검색된 사례는 두 지표가 모두 `0.0`이었다. 도서관 운영 시간은 찾았지만 대출 규정이 청크에서 잘린 사례는 Precision `1.0`, Recall `0.0`이었다. 후자는 검색된 내용 자체는 관련 있지만 정답에 필요한 정보를 모두 포함하지 못한 경우다.

LLM 진단은 원인 후보를 정리하는 보조 수단이다. 실제로 청킹, 색인 누락, 필터 미적용 중 무엇이 원인인지는 원본 문서와 검색 로그를 확인해야 확정할 수 있다.

## 9. 7장 6강: 생성 실패와 환각 분석

생성 단계의 주요 실패 유형은 다음과 같다.

- **환각**: 검색 문맥에 없는 사실을 새로 만든다.
- **문맥 무시**: 필요한 근거가 주어졌지만 답변에 반영하지 않는다.
- **프롬프트 지시 불이행**: 형식, 범위, 인용 등의 명시적 요구를 지키지 않는다.

튜터님 코드는 낮은 생성 지표를 가진 행에 질문, 답변, 검색 문맥을 함께 전달하고 `판정 결과`, `상세 원인`, `품질 개선안`을 생성했다. 환각 사례에 대해서는 근거가 있는 “평일 22시 마감”만 남기고 근거가 없는 주말 개방 정보를 제거하라는 개선안을 도출했다.

실무에서는 다음과 같은 프롬프트 제약을 함께 고려할 수 있다.

```text
- 제공된 문맥만 사용한다.
- 근거가 없으면 모른다고 답한다.
- 각 핵심 주장에 출처를 연결한다.
- 질문과 직접 관련된 내용만 간결하게 답한다.
```

## 10. 7장 7강: 파이프라인 개선과 회귀 검증

회귀 검증은 수정한 실패 사례만 다시 보는 것이 아니다. 이전에 통과했던 사례를 포함한 **동일한 평가셋**을 개선 전후 파이프라인에 모두 실행해야 한다.

```text
고정 평가셋
   ├─ 개선 전 파이프라인 → baseline 지표
   └─ 개선 후 파이프라인 → candidate 지표
                              │
                              └─ 전체·질의 유형·실패 유형별 비교
```

평균 점수가 올라도 특정 질의 유형의 성능이 하락할 수 있다. 따라서 다음을 함께 비교해야 한다.

- 전체 평균과 개별 샘플 점수
- 고유명사형, 의미 탐색형, 복합 조건형별 점수
- Precision 향상에 따른 Recall 하락 여부
- Faithfulness 향상에 따른 답변 유용성 저하 여부
- 평가 비용과 응답 지연 시간

개선안은 한 번에 하나씩 적용하는 것이 원인과 효과를 해석하기 쉽다. 예를 들어 청킹 크기와 프롬프트를 동시에 바꾸면 어느 변경이 점수에 영향을 주었는지 알기 어렵다.

## 12. 핵심 정리

- 검색 방식은 질문 유형에 따라 달라져야 하며, 동적 라우팅도 고정 평가셋으로 검증해야 한다.
- 검색 품질은 Context Precision·Recall, 생성 품질은 Faithfulness·Answer Relevancy로 분리해 본다.
- 좋은 평가셋은 질문, 모범 정답, 근거 문서를 포함하고 다양한 유형과 난이도를 포괄한다.
- LLM 심사 결과는 자동 판정의 근거가 아니라 실패 원인을 좁히는 진단 보조 자료로 사용한다.
- 개선 효과는 동일한 평가셋으로 전후를 비교하고, 평균뿐 아니라 개별·유형별 회귀를 확인해야 한다.
